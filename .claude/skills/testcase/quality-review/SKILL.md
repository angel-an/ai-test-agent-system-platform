# 测试用例质量评审 Skill — 五维质量评审

## 应用场景
- 每批测试用例生成完成后自动执行自检
- 用户要求"审查用例质量"或"评分"
- 用例提交评审前的最终检查
- 测试质量报告生成

---

## 评审维度体系

五维模型依据ISO/IEC 25010质量模型（功能完整性、可靠性、可维护性）与IEEE 829测试文档标准设计，维度间无重叠：

### 维度一：需求追溯完备性（Requirements Traceability Completeness）— 权重30%

**评审重点**：对照需求/PRD功能矩阵，检验用例是否全面覆盖所有功能点、业务流程、规则组合。

#### 分段评分标准

| 得分区间 | 判定标准 | 典型特征 |
|---------|---------|---------|
| 27-30 | 完整覆盖所有功能点与联动规则，含正向+异常+端到端场景 | 每个功能点≥3用例(P0≥3)，有独立联动规则用例，状态机全路径覆盖 |
| 22-26 | 覆盖核心功能点，遗漏1-2个非核心关联规则 | 主流程全覆盖，个别组合规则或可选场景遗漏 |
| 17-21 | 覆盖主要功能点，遗漏联动规则或特殊场景 | 主功能覆盖，联动规则或特殊条件未独立验证 |
| 8-16 | 仅覆盖部分功能点，有明显遗漏 | 核心功能点遗漏，缺少异常场景 |
| 0-7 | 严重遗漏，与需求不符 | 遗漏核心流程，或测试内容与PRD不对应 |

#### 扣分项清单

| 扣分项 | 扣分值 | 判定方式 | 示例 |
|--------|--------|---------|------|
| P0功能无独立用例 | -5分/个 | 功能优先级检查 | P0核心流程"下单支付"无独立正向用例 |
| 正向用例缺少 | -4分/个 | 功能点-用例对照 | 功能点"取消订单"只有异常用例无正向用例 |
| 异常/负向用例缺少 | -3分/个 | 异常场景检查 | 功能点"修改密码"无旧密码错误的异常用例 |
| 联动/组合规则未覆盖 | -5分 | 规则-用例对照 | PRD要求"A与B互斥"但无组合测试 |
| 状态转换路径遗漏 | -4分/条 | 状态机覆盖检查 | 订单状态从"待发货"直接到"已完成"缺少中间态验证 |
| 端到端业务流程缺失 | -5分 | 流程链检查 | 缺少从登录→选购→支付→订单确认的完整路径 |

#### 无PRD文档时的处理

当用户未提供PRD需求文档时，本维度评分改为"自身完整性评估"：
- 30分：用例覆盖完整的业务输入→处理→输出链路，含正向、分支、异常
- 24分：覆盖主流程链路，个别分支遗漏
- 18分：覆盖主要路径，异常路径覆盖不足
- 12分：覆盖部分路径，有明显链路断裂
- 6分：仅覆盖单一场景
- 0分：无法判断与业务的对应关系

同时在评审结果中标注："未提供PRD文档，本维度采用自身完整性评估，分数仅供参考"

#### 行业标准依据
- ISO/IEC 25010: 功能完整性（Functional Completeness）— 功能覆盖程度
- IEEE 829: 测试设计规格说明中要求标识被测试项和功能通过准则
- ISTQB CTFL: 测试覆盖准则要求基于需求的可追溯性矩阵

### 维度二：逻辑结构合规性（Logical Structure Compliance）— 权重25%

**评审重点**：用例逻辑链路是否完整、步骤是否可独立执行、步骤描述是否清晰无歧义。

#### 分段评分标准

| 得分区间 | 判定标准 | 典型特征 |
|---------|---------|---------|
| 22-25 | 步骤完整无跳跃，因果链路清晰，每步只有一个操作，新人可独立执行 | 操作→响应→下一步逻辑连贯，测试数据完整提供，不依赖其他用例结果 |
| 18-21 | 步骤基本完整，有1处小跳跃但不影响理解 | 缺少1个中间操作，但读者可合理推断 |
| 13-17 | 有2-3处跳跃，需读者自行推断中间步骤 | 多处缺少衔接，需结合上下文猜测 |
| 7-12 | 逻辑链路有明显断裂，步骤间缺乏衔接 | 步骤间因果关系不清，无法直接执行 |
| 0-6 | 步骤混乱、逻辑矛盾、无法理解执行流程 | 步骤顺序颠倒、自相矛盾、无法执行 |

#### 扣分项清单

| 扣分项 | 扣分值 | 判定方式 | 示例 |
|--------|--------|---------|------|
| 步骤跳跃（缺少关键中间操作） | -3分/处 | 结构化检查：步骤间缺少必要衔接 | "1.打开支付页面 2.支付成功"——缺少选择支付方式、确认支付 |
| 步骤顺序颠倒导致逻辑不通 | -5分 | 语义推理：结果在原因之前 | "1.验证订单状态为已支付 2.点击支付按钮" |
| 操作与预期结果不对应 | -5分 | 步骤-预期对应检查 | 步骤5的操作在预期结果中无对应验证 |
| 步骤描述模糊无法执行 | -3分/处 | 关键词匹配："进行操作""执行测试"等 | "1.进行正常操作 2.验证功能正常" |
| 步骤少于2步 | -5分 | 数量检测 | 整个用例只有1步操作 |
| 循环引用或自相矛盾 | -8分 | 语义推理 | 步骤3依赖步骤5的结果 |
| 测试数据未完整提供 | -3分/处 | 依赖数据时无具体值 | "输入有效用户名" —— 未给出具体值 |
| 用例与环境强耦合 | -2分 | 依赖特定环境但无说明 | "访问http://localhost:8080" — 未说明环境部署要求 |

#### 清𥈟步骤标准
每步操作要求：
- 每步只有一个原子操作（一个点击、一个输入、一此判断）
- 步骤数量合理（3-15步）
- 步骤描述使用"动词+宾语+条件"结构（如"点击登录按钮"而非"然后登录"）

#### 行业标准依据
- IEEE 829: 测试过程规格说明要求步骤清晰、可重现
- ISTQB CTFL: 可执行性（Executability）是测试用例质量的核心属性，确保不同测试人员执行结果一致
- ISO/IEC 25010: 可操作性（Operability）子特性

### 维度三：预期结果正确性（Expected Result Correctness）— 权重20%

**评审重点**：每步的预期结果是否具体、可验证，包含UI表现和数据状态两个层面。

#### 分段评分标准

| 得分区间 | 判定标准 | 典型特征 |
|---------|---------|---------|
| 18-20 | 每步预期结果可验证，包含UI+数据双层面验证，金额/状态/页面元素有具体值 | "订单状态变为'已支付'，扣款金额=99.00元，页面跳转到支付成功页，接口返回code=0" |
| 14-17 | 大部分明确，1-2处使用模糊表述 | 多数预期有具体值，个别用"验证成功"等模糊词 |
| 10-13 | 预期结果存在但多处不够具体，缺乏判定依据 | "页面显示正确""功能正常运行" |
| 5-9 | 预期结果笼统，无法直接验证 | "验证成功""功能正常""页面正确" |
| 0-4 | 缺少预期结果或预期结果与步骤无关 | 空白、"无"、与步骤完全无关 |

#### 扣分项清单

| 扣分项 | 扣分值 | 判定方式 | 示例 |
|--------|--------|---------|------|
| 使用"验证成功""功能正常"等模糊词 | -3分/处 | 关键词匹配 | "验证登录成功"——改为"页面跳转到首页，右上角显示用户名'张三'" |
| 金额/数量未给出具体值 | -4分/处 | 语义推理 | "扣款金额正确"——缺少具体金额"99.00元" |
| 状态判定缺少期望值 | -3分/处 | 语义推理 | "检查订单状态"——未说明期望"已取消" |
| 缺少页面行为验证 | -2分/处 | 结构化检查 | 只写了数据状态，没有页面跳转/提示信息 |
| 缺少数据状态验证 | -2分/处 | 结构化检查 | 只写了页面提示，没有数据/接口层面验证 |
| 预期结果为空 | -8分 | 字段为空检测 | 预期结果字段无内容 |
| 使用主观描述 | -4分/处 | 关键词匹配："美观""合适""适当" | "页面布局美观"——改为"页面元素按Figma设计稿上下居中排列" |

#### 模糊预期结果关键词库（自动检测）

```
验证成功、功能正常、页面正确、操作成功、系统正常、显示正确、
运行正常、正常显示、正常工作、功能可用、页面正常、响应正确、
处理成功、提交成功、保存成功（无具体状态描述时）、正确、成功（无上下文）
```

**一票否决规则**：
- 单条用例预期结果中出现 ≥2 个模糊词 → 该用例直接判为不合格，必须重写
- 用例集中模糊词出现率 > 10% → 五维评审综合评分最高不超过 59 分（强制返回补充）
- **标准要求**：模糊词出现率 ≤ 10%

**模糊词改写示例**：
| 模糊表达 | 优秀改写 |
|---------|---------|
| "保存成功" | "页面跳转至详情页，数据库中新增1条记录，状态字段='已启用'" |
| "显示正确" | "列表第1行显示'XX公司'，字段A='值1'，字段B='值2'" |
| "验证通过" | "接口返回 code=0，data.id=10001，create_time 为当前时间" |
| "处理成功" | "订单状态由'待处理'变为'已处理'，操作日志记录 operator='admin'" |

**模糊词出现率计算**：
```
模糊词出现率 = 含模糊词的用例数 / 总用例数 × 100%（标准要求≤10%）
```

#### 行业标准依据
- IEEE 829: 预期结果（Expected Result）必须包含具体的输出值或状态变化
- ISTQB CTFL: 可验证性（Verifiability）——测试结果必须可通过客观标准判定
- ISO/IEC 25010: 正确性（Correctness）子特性

### 维度四：测试条件完备性（Test Condition Completeness）— 权重15%

**评审重点**：环境、账号权限、测试数据、业务状态等前置条件是否完整且可独立准备。

#### 分段评分标准

| 得分区间 | 判定标准 | 典型特征 |
|---------|---------|---------|
| 13-15 | 环境/账号权限/测试数据/业务状态等前置条件全部明确，可独立准备 | "已登录普通用户账号'张三'（手机号138xxxx），购物车中有商品A（iPhone 15，单价5999元，数量1），账户余额10000元" |
| 10-12 | 基本完整，缺少1项非关键条件 | 有账号和数据，但未说明浏览器版本或运行环境 |
| 7-9 | 缺少2-3项前置条件，需读者自行补充 | 有账号但未说明权限类型和数据状态 |
| 3-6 | 前置条件严重不足，缺少关键数据或权限说明 | 只写"登录系统"，未说明账号类型和数据 |
| 0-2 | 无前置条件或条件与用例无关 | 空白、"无"、"系统已部署" |

#### 扣分项清单

| 扣分项 | 扣分值 | 判定方式 | 示例 |
|--------|--------|---------|------|
| 未说明账号权限/角色 | -3分 | 涉及权限操作但未说明 | 支付用例未说明用管理员还是普通用户 |
| 未说明测试数据状态 | -4分 | 依赖特定数据但未说明 | 订单取消用例未说明订单当前状态（如"待付款"） |
| 未说明环境要求 | -2分 | 涉及特定环境但未说明 | 需要特定支付渠道但未说明环境 |
| 前置条件为空 | -6分 | 字段为空检测 | 前置条件字段无内容 |
| 前置条件与用例无关 | -4分 | 条件无法支撑步骤 | 前置条件"系统已部署"，但用例需要特定数据 |
| 前置条件依赖其他用例结果 | -3分 | 不可独立准备 | "执行TC-001成功的返回值" |

#### 需要前置条件的关键词信号（自动检测缺失）

| 用例中出现关键词 | 前置条件至少应包含 |
|----------|----------------|
| 支付/付款 | 账号余额/支付方式/订单当前状态 |
| 取消/退款/退货 | 订单当前状态 |
| 删除/移除 | 存在的数据项 |
| 修改/编辑/更新 | 已有数据+当前值 |
| 查询/搜索/查看 | 预期匹配的数据已存在 |
| 上传/导入 | 文件类型/大小/格式 |
| 导出/下载 | 数据类型/数量/格式要求 |
| 权限/授权/角色 | 账号角色/权限配置 |
| 批量/多笔/累计 | 数据量说明 |

#### 行业标准依据
- IEEE 829: 测试用例规格说明要求标识前置条件（Pre-conditions）
- ISTQB CTFL: 前置确定（Pre-condition Determination）是测试设计的基础活动
- ISO/IEC 25010: 可重现性（Reproducibility）要求测试条件可独立搭建

### 维度五：边界与异常覆盖度（Boundary & Error Coverage）— 权重10%

**评审重点**：边界值、特殊值、并发竞态、互斥规则、错误处理路径是否充分覆盖。本维度需对照 `sit-testcase-generation-v2` 的 **9维必检清单** 执行，重点关注历史高频遗漏维度。

#### 9维覆盖检查（本维度评审时必须对照）

| 维度 | 检查内容 | 扣分标准 |
|------|---------|---------|
| 正向流 | 每个功能点至少1条正向用例；正向用例占比≤45% | P0功能无正向用例：-5分/处；正向占比>45%：-4分 |
| 反向流 | 每个功能点至少1条反向用例；反向用例占比≥30% | 占比<30%：-4分；功能点无反向用例：-3分/处 |
| 字段边界 | 每个入参字段覆盖长度/精度/枚举/空值/格式；边界用例占比≥10% | 占比<10%：-4分；字段无边界覆盖：-2分/处 |
| P0数量基线 | P0功能点各≥5条（2正+2反+1边界） | 任一P0<5条：-5分/处 |
| 需求溯源 | 每条用例必须标注需求来源 | 无需求来源标注：-2分/处；臆造用例（找不到需求出处）：-5分/处 |
| 数据库异常 | 写操作功能点至少1条（主键冲突/唯一约束/连接失败/事务回滚/查询超时） | 写操作无DB异常用例：-4分/处 |
| 并发安全 | 核心写入/领取/扣减/状态变更至少1条（幂等/竞争/一致性） | 应覆盖但未覆盖：-4分/处 |
| 跨模块一致性 | A输出→B输入的功能点至少1条（格式/关联/同步/防重复/降级） | 应覆盖但未覆盖：-3分/处 |
| 时间边界 | 时间字段/规则至少1条（格式/精度/跨日/范围/精确边界） | 应覆盖但未覆盖：-3分/处 |
| 字段级安全 | 用户输入字段至少1条（SQL注入/XSS/路径遍历/特殊字符/非法URL） | 应覆盖但未覆盖：-4分/处 |
| 三方依赖异常 | 外部API/三方服务至少1条（超时/异常数据/连接失败/重试/局部失败） | 应覆盖但未覆盖：-3分/处 |

**特别注意**：以下字段必须视为用户输入点，不能因"在后台配置"而跳过安全测试：
- OSS 配置的图片 URL、跳转链接
- Banner/广告/弹窗的素材、文案、标题
- 热区坐标、跳转参数
- 活动规则描述

#### 分段评分标准

| 得分区间 | 判定标准 | 典型特征 |
|---------|---------|---------|
| 9-10 | 9维全覆盖，边界值全覆盖（0/负数/最大值/超长），异常路径有独立用例，并发/DB/安全/三方均有覆盖 | 每个输入项有边界测试（+-1），4个历史遗漏维度均有独立用例 |
| 7-8 | 主要维度覆盖较好，1-2个历史遗漏维度有缺失 | 边界值已测试，但DB异常或并发略有不足 |
| 5-6 | 有部分边界值测试，2-3个历史遗漏维度缺失 | 仅有常规边界和反向，无DB/并发/安全深度覆盖 |
| 3-4 | 仅有1-2个边界/异常场景，4个历史遗漏维度大面积缺失 | 几乎只有正常流程+简单反向 |
| 0-2 | 无边界和异常覆盖，纯正向用例 | 所有用例均为Happy Path |

#### 扣分项清单

| 扣分项 | 扣分值 | 判定方式 | 示例 |
|--------|--------|---------|------|
| 数值边界未测试（0/负数/最大值+1/精度边界） | -3分/处 | 涉及数值输入但无边界用例 | 金额输入未测试0元、负数、超过最大值 |
| 空值/null/空字符串未测试 | -2分/处 | 必填字段无空值用例 | 用户名未测试空输入 |
| 特殊字符/注入攻击未测试 | -2分/处 | 文本输入无特殊字符用例 | 搜索框未测试SQL注入(' OR 1=1--) 或 XSS(<script>) |
| 并发/竞态场景缺失 | -4分 | 涉及共享资源但无并发用例 | 未测试同一订单并发支付、同一优惠券并发领取 |
| 错误处理路径缺失 | -3分 | 有异常可能但无错误处理用例 | 网络超时、第三方服务不可用、数据库连接失败等未测试 |
| 互斥条件未测试 | -3分 | 有互斥规则但无对应用例 | 两种优惠券互斥规则未测试同时使用的场景 |
| 长度/格式边界未测试 | -2分/处 | 文本输入未测试最大长度+1/最小长度-1 | 手机号未测试11位/12位/10位各场景 |
| 数据库异常未测试 | -4分/处 | 写操作无DB异常用例 | 提交订单、领取优惠券等写操作无DB异常覆盖 |
| 时间边界未测试 | -3分/处 | 时间字段无精确边界测试 | 48小时复弹只测"48小时后"，未测47h59m/48h01m |
| 三方依赖异常未测试 | -3分/处 | 外部调用无异常用例 | OSS、广告、定位、支付等三方服务无超时/失败覆盖 |
| 反向用例占比<30% | -4分 | 全局统计 | 正向用例过度膨胀 |
| 边界用例占比<10% | -4分 | 全局统计 | 边界覆盖不足 |
| 正向用例占比>45% | -4分 | 全局统计 | 正向用例膨胀，需削减或补充反向/边界 |
| 模糊词出现率>10% | -4分 | 全局统计 | 预期结果模糊，需具体化 |
| P0功能点用例数<5条 | -5分/处 | 逐功能点核对 | 核心功能覆盖不足 |
| 用例无需求来源标注 | -2分/处 | 逐条检查备注 | 无法追溯需求 |
| 臆造用例（找不到需求出处） | -5分/处 | 对照需求矩阵 | 用例脱离需求 |

#### 边界异常场景识别信号词

```
金额/价格/数量/长度/范围 → 边界值测试（0、负数、最大值+1、最小值-1）
必填/不能为空/非空 → 空值/空字符串测试
唯一/不可重复/不重复 → 重复值提交测试
同时/并发/并发数/多人 → 并发测试
互斥/不能同时/只能选一 → 互斥条件测试
超时/失败/异常/故障 → 错误处理测试（网络、第三方、DB）
权限/角色/授权/越权 → 越权访问测试
精确度/小数点/四舍五入 → 精度边界测试
时间/有效期/48小时/24小时/当天/首次 → 时间边界测试
OSS/广告/投放/定位/第三方/外部接口 → 三方依赖异常测试
配置/素材/文案/链接/URL/热区 → 字段级安全测试
```

#### 行业标准依据
- ISO/IEC 25010: 容错性（Fault Tolerance）与成熟度（Maturity）子特性
- ISTQB CTFL: 边界值分析（BVA）是等价类划分的必备补充
- IEEE 829: 测试设计需包含边界条件和错误推测

## 评分一致性原则

1. **同类问题同分**：相同类型的问题在不同用例中应扣除相同分数
2. **扣分累加不超上限**：单个维度的扣分总额不超过该维度满分
3. **最低0分**：任何维度得分不低于0分
4. **整数评分**：所有维度评分取整数
5. **扣分必须注明出处**：扣分必须引用用例中的具体内容位置（如"第3步""前置条件""预期结果第2条"）
6. **红线一票否决**：预期结果字段完全为空或步骤完全不可操作，对应维度直接0分

## 评审流程

```
Step 1: 加载用例集 → 解析用例编号、步骤、预期结果、前置条件等字段
Step 2: 逐维度评审
  2a. 需求追溯完备性 → 对照需求功能矩阵（或自身完整性评估）
  2b. 逻辑结构合规性 → 逐条检查步骤逻辑链路
  2c. 预期结果正确性 → 逐条检查预期结果表述
  2d. 测试条件完备性 → 逐条检查前置条件
  2e. 边界与异常覆盖度 → 全局检查边界/异常场景覆盖情况
Step 3: 汇总评分 → 综合各维度得分
Step 4: 输出报告 → 按模板输出问题清单+修复建议
Step 5: 质量等级评定 → 给出S/A/B/C/D级结论
```
