# SIT 测试用例生成 v2 — 9维覆盖与执行保障

## 定位

本 Skill 是 SIT 功能测试用例生成的**覆盖度强制检查清单**。与现有 `test-case-design`（教你怎么设计用例）、`quality-review`（评审写得好不好）形成互补：

- `test-case-design` → **怎么设计**
- `sit-testcase-generation-v2` → **不能漏什么**
- `quality-review` → **写得对不对**

生成 SIT 用例时，必须**先按本 Skill 检查覆盖维度，再调用 test-case-design 选择设计技术，最后用 quality-review 评审质量**。

---

## 激活场景

- 用户要求生成 SIT 功能测试用例
- 用户在 SIT 模式下进入 Step 4（测试用例设计）
- 每完成一个功能点的用例设计后自检
- Step 5 覆盖度评估时强制对照

**UAT 模式禁止激活本 Skill。**

---

## 核心原则

1. **先保不遗漏，再求写得好**：覆盖度是硬门槛，质量评审是软优化
2. **风险驱动密度**：P0 功能多测，P2 功能少测，但最低基线不能破
3. **反向用例不少于 30%**：防止正向流过载
4. **边界用例不少于 10%**：防止字段边界遗漏
5. **4个历史遗漏维度必须各至少 1 条**：数据库异常、并发安全、时间边界、字段级安全

---

## 风险等级定义（与现有优先级字段映射）

| 风险等级 | 判定标准 | 用例数量基线 | 映射到 priority 字段 |
|---------|---------|-------------|---------------------|
| **P0** | 入口级/核心写入/流程衔接/资金相关/用户高频操作 | ≥ 5 条（至少 2 正 + 2 反 + 1 边界） | 高 |
| **P1** | 状态变更/CRUD 写操作/配置生效/跨模块调用 | ≥ 3 条（至少 1 正 + 1 反 + 1 边界） | 中 |
| **P2** | 纯只读查询/静态配置展示/低频辅助功能 | ≥ 2 条（至少 1 正 + 1 反） | 低 |

> 注意：本 Skill 的 P0/P1/P2 是**测试设计时的风险分级**，输出到 Excel 时仍使用现有 `priority` 字段（高/中/低）。映射关系：P0→高，P1→中，P2→低。

## 9维必检清单（每个功能点逐项检查，不可遗漏）

### 1. 正向流
**覆盖要求**：每个功能点 ≥ 1 条。合法输入 + 完整流程，验证预期结果。

**识别信号**：功能点存在正常业务路径即可触发。

**常见错误**：
- 一个功能点写 5-7 条正向，但反向只有 1 条
- 把不同数据取值都当成正向用例（应拆为边界/等价类）

---

### 2. 反向流
**覆盖要求**：每个功能点 ≥ 1 条。非法输入/业务规则拒绝/参数缺失/权限不足。

**识别信号**：
- 有"必填"、"不能为空"、"必须"等字样
- 有业务规则限制（如"不可叠加"、"仅限一次"）
- 有权限区分（管理员/普通用户）

**映射到现有字段**：`type=异常类测试`，`keyword=反向`。

---

### 3. 字段边界
**覆盖要求**：每个功能点的**每个入参字段**逐字段覆盖以下边界类型中的适用项。

**通用边界类型**：

| 边界类型 | 适用字段 | 典型取值 | 映射 keyword |
|---------|---------|---------|-------------|
| 长度边界 | 字符串/文本 | 最小值/最大值/最小值-1/最大值+1 | 边界 |
| 精度边界 | 金额/小数 | 1位小数/2位小数/3位小数/0.00/负数 | 边界 |
| 枚举值 | 状态/类型/选项 | 每个合法值 + 1 个非法值 + null | 反向/边界 |
| 空值 | 所有输入字段 | null / 空字符串 / 空数组 / 空对象 | 反向 |
| 格式 | 日期/手机号/邮箱/URL | 非法格式、特殊字符、emoji、Unicode异常 | 反向/边界 |
| 数值范围 | 整数/数量/页码 | 0、负数、最小值-1、最大值+1 | 边界 |

**按控件类型的边界细分（B端系统常见）**：

| 控件类型 | 边界场景 | 典型取值 | 说明 |
|---------|---------|---------|------|
| **文本模糊查询** | 空字符串查询 | `""`、`" "` | 应返回全部或提示 |
| | 单字符查询 | `"a"` | 最小有效长度 |
| | 超长查询词 | 255字符、256字符 | 长度边界 |
| | SQL通配符 | `"%"`、`"_"`、`"%test%"` | 模糊查询语法 |
| | 特殊字符查询 | `"<script>"`、`"';--"` | 安全边界 |
| **下拉框多选** | 全不选 | `[]`、null | 必填校验 |
| | 选1个 | `["选项A"]` | 最小选择 |
| | 全选 | 所有选项 | 最大选择 |
| | 选上限+1 | 超过maxSelectCount | 超出限制 |
| | 重复选择 | `["A","A"]` | 去重验证 |
| | 跨页选择 | 第1页选A，第2页选B | 回显验证 |
| | 选项被删除后回显 | 已选选项在数据源中不存在 | 兼容性 |
| **日期范围选择** | 开始=结束 | 同一天 | 边界闭合 |
| | 开始>结束 | 时间倒置 | 业务拒绝 |
| | 跨年/跨月 | 12-31 → 01-01 | 日期计算 |
| | 未来日期 | 明天、明年 | 业务规则 |
| | 极远日期 | 1970-01-01、2099-12-31 | 系统兼容 |
| **开关/单选** | 启用→禁用 | 状态切换 | 正向流程 |
| | 禁用→启用 | 状态切换 | 正向流程 |
| | 快速连续切换 | 3秒内切换5次 | 防抖/幂等 |
| | 默认值验证 | 页面首次加载 | 默认启用/禁用 |
| **级联选择器** | 上级未选 | 直接选下级 | 应禁止或为空 |
| | 中间级缺失 | 省存在、市缺失、直接选区 | 数据完整性 |
| | 回显验证 | 编辑时三级回显 | 数据绑定 |
| | 动态加载 | 上级变更后下级刷新 | 联动验证 |
| **数值区间输入** | 最小值 | 下边界 | 包含/不包含 |
| | 最大值 | 上边界 | 包含/不包含 |
| | 小数精度 | 1.001（限2位小数） | 精度截断/四舍五入 |
| | 负数 | -1 | 业务拒绝 |

**识别信号词**：`长度`、`最大`、`最小`、`必填`、`枚举`、`状态`、`金额`、`数量`、`页码`、`日期`、`手机号`、`URL`、`JSON`、`模糊查询`、`下拉多选`、`开关`、`级联`、`区间`。

**常见错误**：
- 只测"有效值"和"空值"，不测边界±1
- 多个字段合并在一个用例里测（应拆成单字段用例）
- 模糊查询只测"正常关键词"，不测`%`、`_`、空字符串
- 多选只测"选1个"，不测全选、全不选、超上限

### 4. 数据库异常
**覆盖要求**：涉及写操作的功能点，至少 1 条。

**识别信号**：
- 功能点包含"新增"、"保存"、"提交"、"更新"、"删除"、"写入"
- 涉及订单/优惠券/库存/积分/状态变更
- 有事务一致性要求（批量操作）

**强制覆盖场景（至少选 1）**：

| 场景 | 构造方法 | 预期验证 |
|-----|---------|---------|
| 主键/唯一键冲突 | 用相同业务单号重复提交 | 第二次提交被拒绝，不重复落库 |
| 数据库连接失败/超时 | Mock 数据库不可达或慢查询 | 返回明确错误码，不挂起 |
| 事务回滚 | 批量写入中故意让第 N 条失败 | 已写入部分回滚，数据一致性保持 |
| 查询超时 | 列表查询构造大数据量 | 有超时提示或分页兜底 |

**映射到现有字段**：`type=异常类测试`，`keyword=反向`。

---

### 5. 并发安全
**覆盖要求**：核心写入操作至少 1 条。

**识别信号**：
- 功能点涉及"领取"、"扣减"、"下单"、"支付"、"更新状态"
- 同一资源可能被多个用户/多个入口同时操作
- 有"限领"、"库存"、"余额"、"次数"等字样

**强制覆盖场景（至少选 1）**：

| 场景 | 构造方法 | 预期验证 |
|-----|---------|---------|
| 重复请求幂等 | 同一请求在 3 秒内连续发送 2 次 | 第二次被拦截或返回与第一次一致，不重复处理 |
| 多入口资源竞争 | 用户 A 在页面 1 领取，同时在页面 2 再次领取 | 总领取次数/总额不超过上限 |
| 并发状态变更 | 同一订单同时触发"取消"和"支付完成" | 最终状态只有一种，不出现死锁或中间态 |

**映射到现有字段**：`type=异常类测试` 或 `type=性能测试`，`keyword=反向`。

---

### 6. 跨模块数据一致性
**覆盖要求**：涉及 A 模块输出 → B 模块输入的功能点，至少 1 条。

**识别信号**：
- 一个模块配置，另一个模块展示（如后台 OSS 配置 → 小程序首页展示）
- 一个模块生成单号，另一个模块使用（如订单 → 配货单 → 出库单）
- 状态变更需要同步（如用户等级变更 → 首页显示）

**强制覆盖场景（至少选 1）**：

| 场景 | 构造方法 | 预期验证 |
|-----|---------|---------|
| 格式和内容校验 | A 生成的数据在 B 中解析 | B 能正确识别字段值 |
| 关联关系正确 | 追踪单号链路 | 订单号 → 子单号 → 出库单号 可追溯 |
| 状态同步 | 修改 A 的状态后查看 B | B 在合理时间内感知到状态变化 |
| 重复不触发 | A 已处理过的数据再次流入 B | B 不重复处理 |
| 模块链断裂 | A 正常但 B 异常 | A 有降级处理，数据不丢失 |

---

### 7. 时间边界
**覆盖要求**：功能点涉及时间字段或时间规则，至少 1 条。

**识别信号词**：`时间`、`有效期`、`48小时`、`当天`、`首次`、`24小时`、`倒计时`、`开始时间`、`结束时间`、`创建时间`、`更新时间`、`过期`。

**强制覆盖场景（至少选 2）**：

| 场景 | 典型取值 | 说明 |
|-----|---------|------|
| 格式非法 | "abc"、"2024/13/01"、"2024-1-1" | 注意非标准格式 |
| 跨日边界 | 23:59:59 → 00:00:00 | 当天/次日判定 |
| 跨月/跨年 | 月末最后一天、闰年 2 月 29 日 | 日期计算 |
| 时间范围倒置 | 开始时间 > 结束时间 | 业务规则拒绝 |
| 精确边界 | 47h59m / 48h / 48h01m | 如 48 小时复弹规则 |
| 未来/过去极值 | 1970-01-01、2099-12-31 | 系统兼容性 |

**映射到现有字段**：`type=异常类测试` 或 `type=正常类测试`，`keyword=边界`。

---

### 8. 字段级安全
**覆盖要求**：每个包含用户输入的字段，至少 1 条独立安全用例。

**识别信号词**：`输入`、`配置`、`上传`、`URL`、`链接`、`文案`、`素材`、`名称`、`描述`、`备注`、`搜索`、`反馈`、`评论`。

**特别注意**：以下字段看似是配置，实则是用户输入点，**必须覆盖安全测试**：
- OSS 配置的图片 URL、跳转链接
- Banner/广告素材的标题、文案
- 热区坐标、跳转参数
- 弹窗配置内容
- 活动规则描述

**强制覆盖场景（至少选 2）**：

| 攻击类型 | Payload 示例 | 映射 type |
|---------|-------------|----------|
| SQL 注入 | `'; DROP TABLE users; --`、`1 OR 1=1` | 安全性测试 |
| XSS | `<script>alert(1)</script>`、`<img src=x onerror=alert(1)>` | 安全性测试 |
| 路径遍历 | `../../../etc/passwd`、`..\\windows\\system32\\config\\sam` | 安全性测试 |
| 特殊字符 | emoji `🎉`、控制字符 `\x00`、超长中文、RTL 文本 | 异常类测试/安全性测试 |
| 非法 URL | `javascript:alert(1)`、`file:///etc/passwd` | 安全性测试 |

> 安全测试用例的 `keyword` 可写 `反向`（从系统行为角度）或 `边界`（从输入边界角度），但 `type` 必须是 `安全性测试`。

---

### 9. 三方依赖异常
**覆盖要求**：每个涉及外部 API/三方服务/外部配置的功能点，至少 1 条。

**识别信号词**：`OSS`、`广告`、`投放`、`ICC`、`支付`、`定位`、`地图`、`短信`、`推送`、`第三方`、`外部接口`、`回调`、`Webhook`。

**强制覆盖场景（至少选 1）**：

| 场景 | 构造方法 | 预期验证 |
|-----|---------|---------|
| 接口超时 | Mock 响应延迟 > 超时阈值 | 返回超时提示，不阻塞主流程 |
| 返回异常数据 | 返回格式错误/字段缺失/空响应/非 200 状态码 | 系统能容错，不崩溃 |
| 连接失败 | Mock 服务不可用 | 有降级策略（如展示默认图、隐藏模块） |
| 重试机制 | 首次失败，第二次成功 | 自动重试后最终成功 |
| 部分依赖失败 | 调用多个外部接口时部分失败 | 失败部分不影响其他部分 |

## 可选扩展维度（按需触发）

以下维度**不属于9维必检基线**，仅在PRD明确涉及对应场景时才触发。不触发时标注 `N/A`，无需覆盖。

### 扩展1：三方同步业务场景
**触发条件**：PRD中明确出现"同步外部系统"、"对接三方"、"状态同步"、"联动"等字样。

**识别信号词**：`同步`、`对接`、`外部系统`、`状态同步`、`启用禁用联动`、`增量同步`、`全量同步`、`定时同步`、`数据推送`、`数据拉取`。

**强制覆盖场景（涉及同步时至少选 2）**：

| 场景 | 构造方法 | 预期验证 |
|-----|---------|---------|
| 状态同步正向 | 三方系统修改状态后，本系统刷新查看 | 本系统状态与三方一致 |
| 启用禁用联动 | 三方禁用某数据，本系统对应数据自动禁用 | 联动生效，不可手动反启用 |
| 同步延迟边界 | 三方修改后立即查看本系统 | 在承诺的延迟时间内同步完成 |
| 同步冲突 | 本系统和三方同时修改同一数据 | 以某一方为准，数据不丢失 |
| 增量同步 | 只变更一个字段，触发同步 | 仅该字段更新，其他字段不变 |
| 全量同步 | 初始化或定时全量刷新 | 数据完整，无遗漏无重复 |
| 同步失败补偿 | Mock 同步接口失败，观察补偿机制 | 有重试/告警/人工补偿入口 |

**不触发时标注**：`N/A（无三方同步）`

---

### 扩展2：数据权限与隔离
**触发条件**：PRD中出现多角色、多组织、数据可见范围、脱敏等描述。

**识别信号词**：`权限`、`角色`、`组织`、`门店`、`数据隔离`、`脱敏`、`可见`、`可操作`、`范围`、`管辖`。

**强制覆盖场景（涉及权限时至少选 2）**：

| 场景 | 构造方法 | 预期验证 |
|-----|---------|---------|
| 行级权限 | 用户A登录，查看列表数据 | 只能看到自己/本组织的数据 |
| 字段级权限 | 普通用户 vs 管理员查看同一页面 | 敏感字段（成本价等）是否隐藏 |
| 组织隔离 | 总部用户 vs 区域经理查看列表 | 数据范围是否正确（全部 vs 辖区） |
| 数据脱敏 | 查看包含手机号/身份证的页面 | 中间位显示为*，格式保留 |
| 操作权限 | 有查看权限但无编辑权限的用户 | 编辑按钮隐藏或点击提示无权限 |
| 越权访问 | 直接URL访问无权限的数据 | 返回403或重定向到无权页面 |

**不触发时标注**：`N/A（无多角色/数据隔离）`

---

### 扩展3：导入与导出
**触发条件**：PRD中出现Excel导入、Excel导出、批量导入、模板下载等功能。

**识别信号词**：`导入`、`导出`、`Excel`、`批量上传`、`模板下载`、`数据迁移`。

**强制覆盖场景（涉及导入导出时至少选 2）**：

| 场景 | 构造方法 | 预期验证 |
|-----|---------|---------|
| 模板格式错误 | 上传非Excel文件（如.txt、.pdf） | 提示"请上传Excel文件" |
| 字段缺失 | 模板缺少必填列 | 提示缺少XX列，导入失败 |
| 数据类型错误 | 数字列填文本、日期列填非法格式 | 该行导入失败，错误明细可下载 |
| 重复数据 | 模板中有2行相同主键 | 第二行覆盖或跳过，有提示 |
| 大数据量导入 | 一次性导入10000条 | 分批处理，不超时，进度可查看 |
| 部分成功部分失败 | 10行中3行错误 | 7行成功导入，3行错误可下载明细 |
| 导出字段权限 | 无权限字段不应导出 | 导出的Excel中不包含敏感字段 |
| 导出特殊字符 | 数据中包含emoji、换行、制表符 | 导出后不乱码、格式正确 |
| 大数据量导出 | 导出10万条数据 | 异步导出、进度通知、不阻塞页面 |

**不触发时标注**：`N/A（无导入导出功能）`

## 4条硬性规则（必须遵守）

### 规则1：强制覆盖4个历史连续遗漏维度

以下 4 个维度在历史生成中连续遗漏，本次必须保证**每个功能点至少各 1 条**（只要该功能点涉及对应场景）：

| 维度 | 触发条件 | 最低要求 | 优秀标准（推荐） |
|-----|---------|---------|----------------|
| 数据库异常 | 功能点涉及写操作 | ≥ 1 条 | 有即可 |
| 并发安全 | 功能点涉及核心写入/领取/扣减/状态变更 | ≥ 1 条 | 有即可（至少1条，不强制占比） |
| 时间边界 | 功能点涉及时间字段或时间规则 | ≥ 1 条 | 有即可 |
| 字段级安全 | 功能点包含用户输入字段 | ≥ 1 条 | 有即可（每个含用户输入字段的功能点至少1条，安全用例总数≥1条即可，不强制比例） |

**判定方法**：对每个功能点，输出覆盖标记表：

```
| 功能点 | DB异常 | 并发 | 时间 | 安全 | 备注 |
|-------|--------|------|------|------|------|
| 领取优惠券 | ✅ | ✅ | ✅ | ✅ | |
| 查看Banner | ❌ | ❌ | ❌ | ✅ | 纯展示无DB/并发/时间 |
```

未覆盖的必须补充，不得以"用例已经够多"为由跳过。

---

### 规则2：边界用例比例硬性要求

- 边界用例占总用例比例 **≥ 10%**
- 如果生成完成时 < 10%，必须补充边界用例直到达标
- 每个入参字段的边界值必须独立覆盖

**计算方法**：
```
边界用例占比 = keyword=边界的用例数 / 总用例数 × 100%
```

---

### 规则3：反向用例比例硬性要求

- 反向用例占总用例比例 **≥ 30%**
- 如果生成完成时 < 30%，必须补充反向用例直到达标

**计算方法**：
```
反向用例占比 = keyword=反向的用例数 / 总用例数 × 100%
```

---

### 规则3.5：正向用例比例上限（新增）

- 正向用例占总用例比例 **≤ 45%**
- 如果生成完成时 > 45%，必须削减正向用例（合并重复场景）或补充反向/边界用例
- **禁止**为同一功能点的同一正向路径生成超过 2 条用例

**计算方法**：
```
正向用例占比 = keyword=正向的用例数 / 总用例数 × 100%
```

**削减策略**：
1. 检查是否有"换汤不换药"的正向用例（相同路径仅数据不同）
2. 将重复正向用例合并为 1 条，数据用等价类代表值
3. 释放出的配额用于补充反向/边界/异常用例

---

### 规则4：按风险等级的数量基线

| 风险等级 | 最低条数 | 最低组合 |
|---------|---------|---------|
| P0 | ≥ 5 | 2 正 + 2 反 + 1 边界 |
| P1 | ≥ 3 | 1 正 + 1 反 + 1 边界 |
| P2 | ≥ 2 | 1 正 + 1 反 |

**不达标处理**：
- 如果自检发现某功能点未达标，必须补充用例
- 如果某维度未覆盖，必须补充直到达标
- 不得以"这个点不重要"为由跳过
- **P0 功能点必须逐条核对**，不允许任何 P0 功能点低于 5 条

## 4步生成操作流

### 第一步：读取 PRD，标注风险等级

输出格式：

```markdown
|------|--------|---------|----------------------|-----------|
| 首页-Banner | Banner展示 | P1 | 字段边界、三方依赖、字段级安全 | 4 |
| 优惠券 | 领取优惠券 | P0 | 全9维 | 8 |
```

---

### 第二步：逐功能点生成用例

**禁止一次性生成所有用例再检查**。必须按功能点逐个完成。

**防偷懒规则（必须遵守 - 违反将阻止导出）**：
1. **禁止生成纯展示/纯查询类用例（零容忍）**：以下标题模式**发现一条删除一条**：
   - "XX列表页展示XX字段"、"XX页面显示正确"、"查询XX返回正确结果"
   - "XX列表页显示XX数据"、"XX页面展示正确"、"XX字段显示正确"
   - "XX列表页展示正确"、"XX详情页显示正确"
   列表页/查询页只允许测试：筛选逻辑、排序规则、分页边界、权限过滤、空数据展示、大数据量加载。
2. **正向用例必须有具体验证点**：每条正向用例必须验证一个具体的业务规则或数据逻辑，不能只是"页面能打开"。
3. **强制生成顺序：先反向后边界再正向**：每个功能点**必须先生成反向流用例，再生成字段边界用例，最后补充正向流**。禁止跳步先生成正向。
4. **实时比例硬刹车**：每完成一个功能点，**立即计算全局**正向/反向/边界比例。
   - 正向占比 > 45%：**立即停止生成正向**，强制补充反向或边界
   - 边界占比 < 10%：**禁止生成新的正向**，优先补充边界
   - 反向占比 < 30%：**禁止生成新的正向**，优先补充反向
5. **模糊词零容忍**：每生成一条用例，**立即检查预期结果**。发现"正确/成功/正常/验证成功/功能正常/页面正确"等模糊词，**该条当场作废重写**，不得入库。
6. **9维强制覆盖**：每个功能点的9维覆盖表中，❌（未覆盖）的维度必须在进入下一个功能点前补充，不得以"用例已足够"为由跳过。
7. **模块分布均衡性**：
   - 单个模块用例数 ≤ 总用例数的 **25%**
   - 最大模块 / 最小模块 ≤ **5倍**（参考，不作为硬性拦截条件）
   如果超过，削减该模块最弱的正向用例。

按功能点逐个完成：
1. 为该功能点加载 `test-case-design` skill，选择设计技术
2. **按 9 维清单逐项生成，禁止跳过任何维度**
3. 每完成一个功能点，立即输出覆盖标记表
4. 发现遗漏立即补充，再进入下一个功能点

**输出格式**：

```markdown
## 功能点：XXX

### 已生成用例
[用例列表]

### 9维覆盖标记
| 维度 | 覆盖 | 用例编号 | 说明 |
|------|------|---------|------|
| 正向流 | ✅ | TC-XXX-001 | 必须有具体业务规则验证点 |
| 反向流 | ✅ | TC-XXX-002 | |
| 字段边界 | ✅ | TC-XXX-003 | |
| 数据库异常 | ✅ | TC-XXX-004 | 写操作必须覆盖 |
| 并发安全 | ❌ | 待补充 | 核心写入必须覆盖 |
| 跨模块一致性 | N/A | 无跨模块 | |
| 时间边界 | ✅ | TC-XXX-005 | 时间字段必须覆盖 |
| 字段级安全 | ✅ | TC-XXX-006 | 用户输入必须覆盖 |
| 三方依赖异常 | ✅ | TC-XXX-007 | 外部调用必须覆盖 |

**覆盖标记规则**：
- ❌ = 必须补充（该维度适用但未覆盖）
- ✅ = 已覆盖
```

## 常见陷阱与规避

### 陷阱1：功能点内部平均分配
不要在每个功能点下平均分配用例数。核心功能点（P0 级、写操作、跨模块调用）应配更多用例，次要功能点（纯查询、配置读取）适度即可。

### 陷阱2：忽略已有参考用例集
如果提供了一份已有用例集，不要重新从 PRD 白手起家。先提取老用例集的有效场景，补充缺失维度。

### 陷阱3：纯功能思维的"非功能黑洞"
生成时容易将所有精力放在功能覆盖上，遗漏非功能需求。必须在生成完成后对照 PRD 的"非功能需求"章节逐条检查。

### 陷阱4：入参定义遗漏
PRD 中的参数说明表包含了完整的字段定义。生成前必须确保已读取所有参数表，按每个字段的 type/length/required/default/description 逐字段生成边界值用例。

### 陷阱5：模块间的边界不清
A 模块最后一步和 B 模块第一步之间的边界往往是盲区。例如 A 写库成功后触发 B 转换——这个"触发"边界是容易遗漏的验证点。

### 陷阱6：正向用例膨胀（高危）
当没有明确限制时，模型容易生成大量正向用例。**根本原因**：正向用例最容易写（"输入有效数据，期望成功"），反向/边界/异常需要更多思考。

**规避方法**：
1. 每个功能点**强制先生成反向和边界**，达标后再补充正向
2. 实时计算比例：每生成5条用例检查一次比例
3. 正向用例标题必须包含具体验证点（如"状态从A变为B"），不能只是"保存成功"
4. 如果正向占比超过45%，**立即删除**最弱的正向用例（保留有具体业务规则验证的）

### 陷阱7：把"配置"当成"无输入"
OSS 配置、Banner 素材、广告文案、弹窗内容都是**用户输入点**，必须按字段级安全覆盖。不能因为它们在后台配置就认为"没有用户输入"。

### 陷阱8：忽略"可选扩展维度"的触发条件
看到PRD中有"同步"、"权限"、"导入导出"等字样时，必须激活对应的扩展维度检查。不能因为它们不是9维基线就跳过。

### 陷阱9：新增功能不验证字段边界
新增功能（如门店档案）的所有字段都是新字段，必须逐字段覆盖边界值。不能因为"看起来简单"就减少用例。

### 陷阱10：状态切换只测一次
启用/禁用、显示/隐藏等状态切换操作，必须测：启用→禁用→再启用 的完整循环，以及快速连续切换的稳定性。

### 陷阱11：LLM偷懒生成"展示类"用例（新增 - 高危）
**现象**：大量生成"XX列表页展示XX字段"、"XX页面显示正确"、"查询XX返回正确结果"类用例。
**危害**：这类用例没有测试价值，占用配额，挤压反向/边界/异常的覆盖空间。
**零容忍规则**：
1. 生成每条用例前自检：标题是否包含"展示/显示/查询返回/页面"等词且没有具体业务规则？如果是，**直接丢弃不写**。
2. 列表页/查询功能的测试重点应该是：筛选条件组合、排序规则、分页边界、权限过滤、大数据量加载——而不是"能不能显示"。
3. 如果需求文档中只有"列表页展示字段X"的描述，没有更多业务规则，该功能点降为P2，只生成2条用例（1正1反）。
4. 自检正则：`.*(列表页|页面|字段).*(展示|显示|正确).*` 匹配的标题一律删除。

### 陷阱12：字段级安全覆盖不足（新增）
**现象**：整个用例集只有1-2条安全测试用例。
**危害**：用户输入点（包括后台配置字段）存在SQL注入、XSS等风险未覆盖。
**规避方法**：
1. 识别所有含用户输入字段的功能点：名称、描述、备注、搜索框、配置项、URL、文案等
2. **每个含用户输入字段的功能点至少生成1条独立安全用例**
3. 安全用例必须使用真实Payload，如 `'; DROP TABLE users; --`、`<script>alert(1)</script>`
4. 安全用例总数≥1条即可，不强制比例

### 陷阱13：模块分布失衡（新增）
**现象**：某个模块用例数占总数的30%-40%，其他模块严重不足。
**危害**：核心模块过度覆盖，次要模块遗漏，测试资源浪费。
**规避方法**：
1. 每生成一个模块的用例后，计算该模块占比
2. 如果超过25%，暂停该模块，优先补充其他模块
3. 削减策略：删除该模块中标题最弱（最接近纯展示类）的正向用例
   4. 模块分布≤25%为硬性标准，超过需调整
