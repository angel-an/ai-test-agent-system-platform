# 测试用例设计方法论 Skill

## 激活场景
- 需要为具体功能点生成测试用例
- 用户要求设计某模块或接口的测试用例
- 评估现有用例是否覆盖足够的设计维度

---

## 综合测试设计策略与原则

**设计原则**：
1. **代表性**：覆盖合理/不合理、合法/非法、边界/越界及极限输入和环境。
2. **有效性**：步骤描述清晰、无模棱两可或重复话语，按顺序编写以提高执行效率。
3. **完整性**：覆盖所有需求点，完全理解需求。
4. **可复用性**：将相似功能的用例抽象归类，支持重复使用。
5. **可判定性**：执行结果的正确性是可判定的，有相应期望结果。
6. **可再现性**：同样用例，执行结果应当相同。

**综合策略（设计步骤）**：
1. **必须使用边界值分析**：任何情况下都必须使用边界值分析，发现错误能力最强。
2. **补充等价类划分**：必要时用等价类划分方法补充测试用例。
3. **因果图/判定表**：如果程序说明中含有输入条件的组合情况，一开始选用因果图法。
4. **追加错误推测**：用错误推测法追加测试用例。
5. **检查覆盖程度**：对照逻辑检查覆盖程度，未达标准需补充。
6. **顺序建议**：基本功能 -> 边界值 -> 状态转换 -> 错误猜测 -> 异常 -> 性能。

## 9大测试设计方法

### 1. 等价类划分方法
**原理**：将输入域划分为有效等价类与无效等价类，每类取代表性值进行测试。

### 2. 边界值分析方法
**原理**：在等价类边界处取值，包括略小、等于、略大于边界的值。这是最优先且必须使用的方法。

### 3. 错误推测方法
**原理**：基于经验和直觉推测可能出现错误的场景（如特殊空白字符、并发操作、0字节文件等）。

### 4. 因果图方法
**原理**：适合描述对于多种输入条件组合的测试方法，根据输入条件的组合、约束关系和输出条件的依赖关系，画出因果图。

### 5. 判定表驱动分析方法
**原理**：用于多条件组合的业务规则测试，建立判定表穷举条件与动作的组合。

### 6. 正交实验设计方法
**原理**：当输入数据组合庞大时，利用正交表选取具备代表性的组合进行测试，减少测试量但保持高覆盖率。

### 7. 功能图分析方法
**原理**：通过状态迁移图（状态转换）模型来生成测试用例，涵盖所有状态和转换路径。

### 8. 场景设计方法
**原理**：模拟真实用户操作路径，串联多步骤的端到端场景（基本流 + 备选流/异常流）。如订单开单流程、退货流程验证。

### 9. 破坏性测试法
**原理**：
- 异常值输入：系统认为是错误的值。
- 故障植入：置于资源不足等问题环境中（如CPU/硬盘不足）。
- 增加数据量：大批量导入或显示数据。
- 重复操作：连续点击50次，连续导入500次。
*(注：破坏性测试需在测试环境且核心功能完成后执行)*

## 公司标准测试用例模板

在输出测试用例时，**必须严格遵守**以下字段定义与格式要求：

### [用例编号]：应用端-模块[用例名称]

> **module / 所属模块**：必填字段，值为当前用例所属的功能模块名称（如"企业充值"、"会员管理"），必须从需求文档的功能矩阵中提取。

| 字段 | 内容规范与示例 |
|------|------|
| **用例编号** | 模块汉语拼音首字母大写+四位流水号（例：HTWH0001） |
| **功能模块 / module / 所属模块** | **必填**。最低层次的上一级模块名称，需与测试大纲一致。值必须从需求文档的功能矩阵中提取，不可留空。 |
| **用例名称** | **必须**带 `应用端-模块` 前缀，格式：`应用端-模块[动词][操作对象][条件/场景]`。目的：通过用例标题即可快速识别该用例归属的客户端及验证目标。**应用端**常见取值：Web端、APP端（iOS）、APP端（Android）、小程序端、H5端、PC客户端、管理后台、开放平台、API接口 等，根据实际项目选用。**模块**为被测功能所在的业务模块名称，如：登录模块、订单模块、支付模块、权限模块 等。示例：Web端-登录模块-输入正确账号密码登录成功、APP端（iOS）-订单模块-提交订单后库存扣减验证、管理后台-权限模块-普通用户无法访问管理页面。用例标题中的"模块"必须与 `module / 所属模块` 字段值一致。 |
| **测试检查要点** | 简明概括本用例的测试关注点/测试重点 |
| **测试类型** | 必选其一：正常类测试 / 异常类测试 / 兼容性测试 / UI/用户体验测试 / 业务流程测试 / 安全性测试 / 性能测试 |
| **关键词** | 必选其一：正向 / 反向 / 边界。正向=验证预期行为；反向=验证异常/拒绝行为；边界=验证临界/极限值。**独立字段，不要写进备注** |
| **优先级** | 必选其一：高 / 中 / 低（高：首轮必执，核心功能；中：较重要，潜在延期风险；低：一般功能，异常情况） |
| **前置条件** | 执行前提（如：使用Chrome浏览器）。无则可空，有则必填 |

**输入数据**：
- 影响测试结果的关键数据，非核心参数可标注"默认"。

**测试步骤**：
1. 语言通顺、不带感情色彩。格式要求明确操作位置与动作，如：单击“XX 按钮/菜单”，菜单路径使用“->”分隔。
2. 强调内容使用“【】”或“""”标识。

**预期结果**：
1. [具体、可验证的结果，必须描述成功/失败的具体表现（提示文案、状态等）]
2. [不可使用"页面正常显示"、"登录成功"等模糊词]

## 设计质量红线

❌ **禁止出现**以下情况（如出现需立即修正）：
- 预期结果使用"正确显示"、"正常运行"、"成功"等无法客观验证的描述
- 测试类型与优先级使用了非标准选项（如写了P0/P1，而未写高/中/低）
- 步骤中使用"等待片刻"、"稍后"等无法量化的时间描述
- 缺少关键测试数据导致用例无法独立执行
