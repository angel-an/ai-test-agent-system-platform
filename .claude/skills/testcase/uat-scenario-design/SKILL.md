# UAT 业务场景验收用例设计 Skill

## 激活场景

仅在 **UAT 模式** 下激活。判定信号：
- 用户消息明确出现：`UAT` / `验收用例` / `业务场景用例` / `E2E验收` / `端到端验收`
- 用户在 SIT 用例完成后追加："再补一份 UAT" / "加上验收用例"

弱信号（仅含"验收"二字、上下文模糊）→ **先反问澄清**，确认是 UAT 后再激活本 skill。

---

## UAT 与 SIT 的视角差异（必须先理解）

| 维度 | SIT（功能测试） | UAT（验收测试） |
|------|---------------|---------------|
| 谁来写 | 测试工程师 | 测试工程师协助业务方 |
| 谁来执行 | 测试工程师 | 业务方 / 产品 / 客户 |
| 视角 | 功能点 / 字段 / 边界 | 业务流程 / 用户故事 / 端到端 |
| 颗粒度 | 单功能原子用例 | 多节点串联的业务场景 |
| 关注点 | "代码是否正确实现需求" | "需求是否真的解决业务问题" |
| 设计技术 | 等价类 / 边界值 / 决策表 / 状态迁移 | 业务流程图 / 用户故事映射 / 跨系统调用链 |
| **跳过** PPDCS / KUFI 标注 | 否（必须标注） | **是**（UAT 不输出 PPDCS 维度和 KUFI 象限） |

**关键原则**：UAT 用例不验证"按钮颜色对不对、字段长度边界",只验证"业务能不能跑通、跨系统数据对不对、流程结果符不符合业务预期"。

## 输出数据模型（严格对齐导出工具）

每个业务场景为一个 dict，多节点是嵌套 list。这是 `stage_uat_scenarios` 工具接收的格式：

```json
{
  "biz_code": "X001",
  "category": "业务单据——盘盈盘亏单",
  "biz_type": "盘盈盘亏",
  "biz_description": "实物库存与账面库存不一致，提供调整账面库存的能力",
  "scenario_description": "盘盈盘亏单，盘盈盘亏（盘盈）",
  "steps": [
    {
      "seq": 1,
      "preconditions": "新增盘盈盘亏单，调整类型=\"增加\"",
      "scenario_note": "盘盈盘亏单，盘盈盘亏（盘盈）",
      "action": "操作路径：供应链—业务单据—盘盈盘亏单：\n在盘盈盘亏单列表中点击【新增】，填写好各项信息后点击【保存】",
      "involved_systems": "",
      "expected_result": "在列表生成盘盈盘亏单，状态为\"待提交\""
    },
    {
      "seq": 2,
      "preconditions": "",
      "scenario_note": "",
      "action": "提交盘盈盘亏单，在列表行点击【提交】",
      "involved_systems": "",
      "expected_result": "更新盘盈盘亏单状态为\"待外部审核\""
    }
  ]
}
```

### 字段写法约定

| 字段 | 必填 | 写法要点 |
|------|------|---------|
| `biz_code` | 是 | 全局自增流水：X001、X002、X003…（不要按分类各起一组） |
| `category` | 是 | 二级分类，含中文破折号格式："业务单据——XX单"、"会员管理——XX" |
| `biz_type` | 是 | 简短业务类型名，如"盘盈盘亏"、"会员充值"、"积分兑换" |
| `biz_description` | 是 | 一句话讲清业务的目的（"做什么用的"），不要写实现细节 |
| `scenario_description` | 是 | 描述具体场景，常见格式："{业务类型}，{业务类型}（{分支条件}）"，例："盘盈盘亏（盘盈）"、"盘盈盘亏（盘亏）" |
| `steps[].action` | 是 | 完整操作路径 + 动作。允许换行 \n，强调用【】，引号用 ""。例："操作路径：供应链—业务单据—盘盈盘亏单：\n点击【新增】..." |
| `steps[].expected_result` | 是 | 必须可验证。包含：单据状态变化、库存变动、流水生成、跨系统调用、回退分支。多结果用 1）...\n2）... 分点 |
| `steps[].involved_systems` | 视情况 | 涉及外部系统时填，如 "OA"、"ERP"、"财务系统"；纯前端操作留空 |
| `steps[].preconditions` | 视情况 | 同场景内首节点必填，后续节点继承时留空（视觉合并效果） |
| `steps[].scenario_note` | 视情况 | 同上，首节点写出，后续节点留空 |

## 设计四步法（UAT 模式专用，跳过 PPDCS/KUFI）

### Step U1：业务流程梳理
1. 从需求文档中识别主流程（happy path）和所有分支（异常、回退、跨系统、权限切换）
2. 每条流程画出"起点 → 节点1 → 节点2 → ... → 终点"的链路图（文字描述即可）
3. 标注每个节点的涉及中心（前端 / 后台 / OA / ERP / 财务 / 第三方）

### Step U2：场景拆分（biz_code 编排）

**必须先输出场景枚举表，再生成 biz_code。**

#### 场景枚举表（强制输出）

在拆分 biz_code 前，输出以下表格：

```markdown
### 场景枚举表

| 编号 | 场景类型 | 场景描述 | 是否必须 | 对应 biz_code | 状态 |
|------|---------|---------|---------|--------------|------|
| 1 | 主流程 | {根据实际业务填写，如：正常审批通过} | 是 | X001 | 待生成 |
| 2 | 异常分支 | {根据实际业务填写，如：审批拒绝} | 是 | X002 | 待生成 |
| 3 | 回退流程 | {根据实际业务填写，如：撤回后重新提交} | 是 | X003 | 待生成 |
| 4 | 跨系统 | {根据实际业务填写，如：OA回调失败} | 是 | X004 | 待生成 |
| ... | ... | ... | ... | ... | ... |

**总场景数**: N 个（主流程 A + 异常分支 B + 回退 C + 跨系统 D）
```

**枚举规则**：
- 从 Step U1 的业务流程链路图中提取每一条独立业务流
- 同一业务的主流程 / 异常 / 回退 / 跨系统失败 通常拆成多个相邻 biz_code
- 不要把一条流程塞进一个 step，也不要把多条无关流程合到一个 biz_code
- **禁止跳过枚举表直接生成 biz_code**

#### 分批生成与状态跟踪

按场景类型分批生成，每完成一批更新枚举表状态：

```markdown
### 生成进度跟踪

| 批次 | 场景类型 | 计划生成 | 已 stage | 核对状态 |
|------|---------|---------|---------|---------|
| 第一批 | 主流程 | 2 | 2 | ✅ |
| 第二批 | 异常分支 | 3 | 3 | ✅ |
| 第三批 | 回退流程 | 2 | 1 | ❌ 需补充 X005 |
| 第四批 | 跨系统 | 1 | 1 | ✅ |
```

**每批生成后必须**：
1. 调用 `stage_uat_scenarios` 入库
2. 调用 `list_staged_uat_scenarios` 核对累计数量
3. 在枚举表中将"待生成"更新为"已完成"
4. 如果累计数量 < 计划数量，说明有遗漏，立即补充

#### biz_code 编排规则
- 每条独立业务流 = 一个 biz_code
- 全局自增流水：X001、X002、X003…（不要按分类各起一组）
- 禁止跳号或重置编号

### Step U3：流程节点拆解（steps 编排）
每个 step 应满足：
- 原子性：一个节点 = 一个用户动作（点击/提交/审批） + 一个明确预期
- 可执行性：业务方拿着用例就能照做，不需要再问技术细节
- 可验证性：预期结果能被业务方直接看到（单据状态、库存数值、通知到达）

节点数量参考：
- 简单单据流程（创建 → 提交 → 审批 → 完成）：4-6 个节点
- 跨系统流程（含 OA/ERP 回调）：6-10 个节点
- 超过 10 个节点 → 考虑拆成多个 biz_code

### Step U4：完整性检查（强制，不达标禁止导出）

导出前必须执行以下检查，**任一不达标必须返回补充**：

#### 4.1 场景数量核对
对照 Step U2 的场景枚举表，输出核对结果：

```markdown
### 场景完整性核对表

| 检查项 | 应生成 | 已 stage | 状态 |
|--------|--------|---------|------|
| 主流程场景 | N | M | ✅/❌ |
| 异常分支场景 | N | M | ✅/❌ |
| 回退/撤销场景 | N | M | ✅/❌ |
| 跨系统场景 | N | M | ✅/❌ |
| **合计** | **N** | **M** | **✅/❌** |
```

**规则**：已 stage 数量 ≥ 应生成数量，否则返回 Step U2 补充。

#### 4.2 biz_code 连续性检查
- 编号必须连续无跳号（X001, X002, X003…）
- 发现跳号说明有遗漏，必须补充缺失编号对应的场景
- 输出检查结果：`biz_code 连续性：X001-X008（8个编号连续）✅` 或 `发现跳号：X003, X005 缺失 ❌`

#### 4.3 场景类型分布检查
- 主流程场景占比 ≤ 50%（避免只生成主流程）
- 异常/回退场景占比 ≥ 25%
- 跨系统/权限场景占比 ≥ 10%
- **不达标处理**：主流程占比过高时，必须补充异常/回退/跨系统场景

#### 4.4 节点质量检查
- 每个场景的 steps 数量 ≥ 3（避免过度简化）
- 每个 step 的 action 和 expected_result 非空
- 跨系统操作的 step 必须标注 involved_systems

#### 4.5 模糊词检查
- 所有 expected_result 中禁止出现"成功""正确""正常""验证通过"等模糊词
- 发现模糊词的场景必须重写后再 stage

**不达标处理**：Step U4 任一检查未达标，必须返回对应步骤补充，禁止进入导出。

### Step U5：导出
1. 确认 Step U4 完整性检查全部通过
2. 调用 `list_staged_uat_scenarios` 向用户展示最终累计清单
3. 用户确认后，调用 `export_all_uat_scenarios(requirement_name="...")` 导出
4. 文件名由工具自动按 `{需求名称}_UAT验收用例_{时间戳}.xlsx` 生成，不要自己拼

## 工具调用规范

| 工具 | 何时用 |
|------|-------|
| stage_uat_scenarios | 每完成一批业务场景立即调用，禁止跳过 |
| list_staged_uat_scenarios | 导出前必须先调用并向用户展示 |
| export_all_uat_scenarios | 用户确认后调用，传 requirement_name |
| clear_staged_uat_scenarios | 仅当用户明确表示"重做"时调用 |

红线：
- UAT 模式下禁止调用 stage_testcases / export_all_testcases（那是 SIT 通道）
- 用例字段中禁止出现 ppdcs_dimension、kufi_quadrant、tp_code、design_technique
- 同一个 biz_code 重复入库会按"后写覆盖"处理；如果是要追加节点，必须把完整 steps 重传

## 质量自检清单（导出前必须全部通过）

1. 场景枚举表已输出，所有"必须"场景状态为"已完成"
2. 每个 biz_code 都有完整的 4 个业务头字段
3. 每个 step 的 action 和 expected_result 都不为空
4. 跨系统节点都标注了 involved_systems
5. 同一业务的"主流程 + 异常 + 回退"都覆盖到了
6. 预期结果不使用"成功""正确""正常"等模糊词
7. 业务编号 X001、X002… 连续无跳号
8. 主流程场景占比 ≤ 50%，异常/回退场景占比 ≥ 25%
9. requirement_name 从用户消息提取，不是"测试用例"等默认值
10. 所有场景已调用 `stage_uat_scenarios` 入库，且 `list_staged_uat_scenarios` 核对数量正确
