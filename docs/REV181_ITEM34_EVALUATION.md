## 第 4 项：扩写必须带断言

### 取证

全库 `name` 以「的必填或非法输入校验」/「的边界条件处理」结尾的用例（=扩写产物）：

| 场景类型 | 总数 | 断言 = 0 | 占比 | 断言 kind 分布 |
|---|---:|---:|---:|---|
| 反向（…必填或非法输入校验） | 119 | **105** | **88%** | `required` 11、`enum` 10 |
| 边界（…边界条件处理） | 119 | **77** | **64%** | `max_length` 82、`boundary` 2、`max_count` 4 |
| 合计 | **238** | **182** | **76%** | — |

**语义对齐是好的**：有断言的 56 条里，反向场景挂 `required`/`enum`、边界场景挂 `boundary`/`max_length`/`precision`，**错配 0 条**。所以问题不在"挂错"，而在"挂不上"。

**92 条已编译进执行链路**（`custom_fields.web_test_id` 非空），其中 **40 条断言为 0**。查 `web_case_link_service.py:675`：

```python
"auto_executable": compile_status == "compiled" and bool(assertions),
```

空断言的扩写用例 `auto_executable=False`，**但 `web_test_id` 已经绑上了**——即"绑定了资产但跑起来什么也验不了"。这类用例在覆盖率报表里不显示为"已覆盖"，但在用例列表里长得和正常用例一样，人工扫一遍很难发现。

### 根因（三处，按影响排序）

**① `_rule_assertions` 按 kind 取断言，取不到就给空列表**

`ai.py:1219`：

```python
_linked_assertions = _rule_assertions(rule).get(assertion_kind, [])
custom_fields["assertions"] = _linked_assertions
if _linked_assertions:
    custom_fields["executable_track"] = "auto"
```

- 反向场景取 `required` 桶 → 字段 `required=False` 且无 `options` 时，桶是空的
- 边界场景取 `boundary` 桶 → 字段无 `range`/`max_length`/`decimal_places` 时，桶是空的

关键：闸门（rev181 第 1 项）只保证"能回链到字段"，**没保证"该字段在这个维度上有约束"**。回链成功 ≠ 有断言可挂。

实测复现：

```
正向 | 1 断言 ['required']  | track=auto   | 限购标签最多8个字
反向 | 1 断言 ['required']  | track=auto   | 限购标签最多8个字的必填或非法输入校验
边界 | 0 断言 []           | track=manual | 限购标签最多8个字的边界条件处理   ← 只有 max_length，无 range
```

**② 反向场景的两个断言来源不对等**

反向场景名为「必填**或**非法输入校验」，但只挂 `required`/`enum`。对「仅支持 jpg/jpeg/png 格式」「(0,1000] 之间的正整数」「字符类型：大小写字母、数字」这类条目，真正的校验是**格式/范围/字符类型**，这些断言在 `boundary` 桶里，反向场景一条都拿不到。

**③ 扩写条件里那个 `not re.search(...)` 反向清单**

```python
and not re.search(r"列表|查询|查詢|点击|點擊|入口|状态|狀態|問卷|问卷|新增题目|拖拽", point)
```

这是历史补丁，用来避免列表类条目的扩写。风险：`状态`/`列表` 这类词在正常业务句里极常见（「状态切换后列表同步」），会把可扩写的条目误拦。rev181 的闸门已经能区分"存在性描述"和"可测行为"，这条清单可收窄为只挡 `列表|入口|点击|拖拽`。

### 建议改法（与"必须带断言"不同）

原方案「扩写必须带断言」有个副作用：会**把 182 条用例从"空壳"变成"消失"**。用户已明确说过"不丢需求"。所以建议：

**生成期按 kind 是否存在决定要不要扩写**，而不是事后校验：

```python
# 伪代码：扩写前先看该字段在目标维度上有没有约束
lrule = _match_field_for_point(point, aliases)
buckets = _rule_assertions(lrule[0]) if lrule else {}

# 反向：只要 required 或 enum 任一非空才扩
if buckets.get("required"):
    scenarios.append((f"{point}的必填或非法输入校验", "反向", ...))

# 边界：只要 boundary 或 max_length/range/precision 非空才扩
if buckets.get("boundary"):
    scenarios.append((f"{point}的边界条件处理", "边界", ...))
```

收益：238 条 → 约 56 条（全部有断言），**且这 56 条本来就在**，不增不减内容，只删空壳。

代价与配套：
- 需求点仍有正向叙述用例兜底（闸门本来就这么保证），不丢需求
- `assertion_gaps` 里增加一条 `"reason": "该字段在 {维度} 维度无约束"`，让"为什么没扩写"可解释
- 需要重新生成受影响用例（库里旧用例不会自愈）

### 额外建议（独立于第 4 项，但同源）

`web_case_link_service.py:675` 的 `auto_executable` 判定是对的，但**绑定时长**不该给空断言用例。建议在绑定时对 `assertion_count == 0` 的用例打 `web_coverage.skip_reason = "no_assertion"` 并在回执里显式计数，避免"绑上了但验不了"沉在列表里。

### 工作量与风险

| 项 | 估计 |
|---|---|
| 改动点 | `_build_requirement_cases` 扩写条件（约 10 行）+ `assertion_gaps` 增补 reason（约 5 行） |
| 回归风险 | 中低：只影响"扩不扩写"，不影响已生成用例。有 `test_case_title_rev181.py` 现成用例可扩展 |
| 需重新生成 | 是。95 条在用用例里 9 条带扩写后缀，全库 238 条 |
| 验收口径 | 扩写场景 `assertion_count > 0` 比例 = 100%（当前 24%） |

## 第 3 项：模糊词替换

### 取证

把模糊词分两档，全量扫 95 条用例标题 + 213 步步骤/预期：

| 档位 | 例子 | 标题命中 | 步骤命中 | 能否机械替换 |
|---|---|---:|---:|---|
| 可测化 | 可正常保存、正常生效、无任何异常、符合预期 | 7（rev181 前）→ **0**（现在） | 0 | 能，rev181 已做 |
| 不可测化 | 合理、友好、流畅、稳定、明确、正确、完整 | **2** | 6 | **不能** |

不可测化的 8 条明细：

| 位置 | 内容 | 是真模糊词吗 |
|---|---|---|
| 标题 TC-249172 | 会员限购商品管理列表完整展示五个业务字段 | 否——"完整展示五个"本身可判定（数 5 个字段） |
| 标题 TC-255903 | 限购周期开始时间与结束时间相同时的行为明确 | **是**——"行为明确"没说是什么行为 |
| 预期 ×4 | 「企业账户充值金额」隐藏或不可用 | 否——"或"是两种预期并列，可判定 |
| 预期 TC-133292 | 保存成功，列表中名称完整展示20字 | 否——"完整展示20字"可判定 |
| 预期 TC-255903 | 按实现给出明确结果：保存成功或提示时间范围非法 | **是**——含"按实现"，等于没给预期 |

真模糊词：**1 条标题 + 1 步预期**，占 95 条用例的 1.1%（8 条命中里 6 条是误报）。

### 为什么建议不做

1. **分母太小**：8 条命中里只有 2 条是真的。为一个 1% 的问题引入一份 20+ 条替换规则表，是为噪声写代码。
2. **机械替换会造新错**：`正确` → ? `完整` → ? `明确` → ? 任何替换都得先知道"正确"的对立面是什么。这类词的正确处理是**退回需求作者补写**，不是平台猜。
3. **rev181 已吃掉可测化的那半边**：`可正常保存 → 可保存`、`正常生效 → 生效`，7 条清零。剩下的是不同性质的问题。

### 替代方案：生成期告警（成本 ~20 行）

不替换，只**标记**。在 `_assign_case_metadata` 里扫标题与步骤预期，命中不可测化词表就写 `custom_fields.vague_terms: ["行为明确"]`，并在生成回执里汇总：

```
VAGUE_TERMS  3 条用例含不可测化表述（TC-249172 标题、TC-255903 预期…）
             建议退回需求方补充判定标准；平台不自动改写，避免编造预期
```

这样：
- 不新增错误（不改写）
- 让问题可见（回执 + 用例字段）
- 与平台"不编造断言"的一贯口径一致（同 `assertion_gaps` 的处理哲学）

## 实施记录：rev182（2026-10-22 落地）

原方案（「按 kind 是否存在决定要不要扩写」）已实现，另修了两处只有落地后才暴露的问题。

### 改了什么

`backend/app/api/v2/ai.py`：

1. **`_assertions_for_scenario(keyword, buckets)`** — 判定「扩不扩」与「挂什么断言」用**同一个函数**。
   反向场景按 `required → condition → boundary` 顺序取第一个非空桶（原逻辑只认
   `required`，导致「只有范围约束」的字段扩了反向却挂 0 条断言）；边界场景只认 `boundary` 桶。
2. **扩写闸门**改为 `if _assertions_for_scenario(...)` 才追加场景，判定顺序调整为
   `unlinked → list_or_nav → no_behavior → no_constraint`（从最具体到最笼统）。
3. **`expand_skips` 回执** — 每个没扩写的点都记 `{point, reason, field?, detail}`，
   `_build_expand_skip_warning()` 转成中文告警随生成回执返回（`expand_skip_warning`）。
4. **`_TESTABLE_VERBS` 补选填语义**：`可以不填 / 无需填 / 非必填 / 不必填 …`
   原先「备注可以不填」被判 `no_behavior`。
5. **`_SUBJECT_DELIM_RE` 补 `--` / `—` / `->` / `→`**（**落地后发现的真缺陷**）：
   「增加会员限购商品管理列表--交易云-运营-增加菜单」的主语区原先覆盖整串，
   里面的「限购商品」被当成主语回链，给"新增菜单"条目挂上「限购商品=必填8字」断言
   —— 与 rev133 假通过同型。

### 实测效果（项目 1169，库中现存 34 条扩写场景）

| 指标 | 改前 | 改后 |
|---|---|---|
| 扩写场景中断言=0 | 25/34（73%） | **0** |
| 同批条目的判定 | 全部扩写 | 8 条扩写且有断言，26 条不扩写 |
| 正向用例（需求点） | 34 | 34（**一条没丢**） |

> ⚠️ 这次改的是**生成期**逻辑，库里旧用例不会自愈——必须重新生成才能拿到新结果。

### 回测与单测

- `.workbuddy/tmp/rev182_backtest.py` — 10 种真实约束形态，空断言扩写 **0 条**。
- `.workbuddy/tmp/rev182_replay.py` — 用库中真实条目重放，空断言 **0 条**。
- `backend/tests/test_expand_assertion_gate_rev182.py`（24 条）— 锁三件事：
  能扩⇔有断言、无约束不扩且原因可解释、有约束不误杀。
  另含 `test_parser_gap_is_not_reported_as_gate_bug`：登记「口语化写法抽不出约束」
  属 `extract_constraints` 的缺口（`仅支持jpg，png格式`、`最多2位小数`、
  `仅当…时显示` 三种），**不是闸门误杀**，避免以后被反复误报。
- 连带改动：`_build_minimal_cases` / `_build_requirement_cases` 返回二元组 → 三元组，
  6 个测试文件共 14 处解包同步。

### 遗留（本次未改）

- `extract_constraints` 不支持：口语格式串、`最多N位小数`、`仅当…显示`。
  这三类字段会被判「无约束」而不扩写——**宁可少生成也不生成空壳**，
  但要补解析层才能让它们重新进入覆盖范围。
