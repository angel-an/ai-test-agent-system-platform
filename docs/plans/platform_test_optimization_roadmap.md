# 平台测试优化路线图

> 目标：把测试用例生成、API 测试、Web 测试三条链路整理成平台级能力，供后续所有项目复用。
> 原则：先统一标准，再固化执行，再接入编排；真实项目只用于验证平台能力，不作为平台规则本身。
> 任务清单见 [platform_test_optimization_tasks.md](./platform_test_optimization_tasks.md)。

## 1. 路线图总览

| 阶段 | 重点 | 平台交付物 | 是否需要真实项目复验 |
|---|---|---|---|
| P0 | 基座统一 | 生成契约、目录规范、报告模板、门控规则 | 不需要 |
| P1 | 用例生成质量 | 质量门禁、知识库引用、覆盖检查、版本留档 | 需要 |
| P2 | API / Web 执行层 | API 分层、Web 稳定脚本、统一证据、编排入口 | 必须 |

## 2. P0 基座统一

### 2.1 目标

把平台共用的规则先定死，避免每个项目重新定义字段、命名和回写口径。

### 2.2 任务单

1. 统一测试用例生成契约
   - 场景、步骤、预期、风险、数据依赖、可执行性字段固定
   - 生成结果必须可直接进入后续 API / Web 执行

2. 统一目录和命名
   - 生成物、回写物、证据包、脚本、任务单固定命名
   - Web / API / 生成三轨分目录管理

3. 统一报告模板
   - 固定通过 / 待复核 / 待确认 / 缺陷 四类结果
   - 固定证据引用位和回写格式

4. 统一门控
   - 默认安全回归
   - 显式 live 开关
   - 风险负向独立门控

### 2.3 验收标准

- 纯规则检查通过
- 目录和命名可直接复用
- 不依赖真实项目 live 复验

### 2.4 真实项目复验

- 不需要
- 这一阶段只做平台规则整理，不做业务写入

## 3. P1 用例生成质量

### 3.1 目标

让 AI 生成的测试用例稳定、可审、可执行，不依赖人工大修。

### 3.2 任务单

1. 固化生成提示词
   - 步骤与预期结果成对出现
   - 禁止模糊断言
   - 明确知识库引用来源

2. 增加生成后质量门禁
   - 缺 `result` 拒绝
   - 模糊词扫描
   - 重复场景检查
   - 覆盖缺口检查

3. 固化场景版本
   - 生成结果按版本号留档
   - 版本变更时能对比差异

4. 输出生成质量报告
   - 场景数量
   - 覆盖比例
   - 缺失项
   - 可执行率

### 3.3 验收标准

- `result` 完整率 100%
- 模糊断言 0
- 场景可直接进入 API / Web 执行层

### 3.4 真实项目复验计划

必须做，建议至少覆盖 2 类真实项目：

1. 文档型项目
   - 验证需求整理版是否能稳定转成可执行用例
   - 看知识库检索是否能支撑场景拆分

2. 流程型项目
   - 验证多步骤、状态机、边界条件是否能稳定生成
   - 看步骤级预期是否能保持完整

#### 复验检查点

- 生成条数是否稳定
- 步骤与预期是否成对
- 是否有模糊断言
- 是否能直接进入 API / Web 执行
- 是否需要人工补写或大修

#### 复验退出条件

- 两类项目均通过
- 生成结果能稳定落库
- 后续执行层不再依赖人工补齐结构

## 4. P2 API / Web 执行层

### 4.1 目标

让生成的用例真正变成可复跑资产，并且在真实项目里得到一致结论。

### 4.2 任务单

1. API 分层固定
   - 准入 / 查询 / 写入 / 复合 / 负向 / 收口
   - 单接口测规则，复合场景测闭环

2. Web 稳定层固定
   - 主链路
   - 分层回归
   - 负向隔离
   - 结果回写

3. 统一证据链
   - Web：截图、self_reflect、页面明细
   - API：返回体、DB / 流水、pytest 报告
   - 编排：统一执行报告

4. 编排入口
   - 一条指令选场景
   - 自动分轨执行
   - 自动聚合回写

### 4.3 验收标准

- API：状态码、返回体、DB / 流水一致
- Web：页面流程、明细、结果弹窗一致
- 编排：能自动串起选场景、执行、回写

### 4.4 真实项目复验计划

必须做，且按三步走：

1. API 只读复验
   - 先跑准入和查询
   - 确认鉴权、隔离、字段口径

2. API live 小额复验
   - 再跑写入、复合、负向门控
   - 确认余额、流水、成功数、失败清单一致

3. Web live 复验
   - 先主链路
   - 再分层回归
   - 最后冻结基线

#### 复验检查点

- 页面和接口结论一致
- 负向用例不产生脏流水
- 结果能回写成稳定基线
- 编排能串起 Web 和 API 双轨

#### 复验退出条件

- 至少 1 个真实项目完成 API + Web 双轨验证
- 生成结果、执行结果、回写结果三者闭环
- 可以冻结为平台基线

## 5. 推荐执行顺序

1. 先做 P0，统一平台标准
2. 再做 P1，补强生成质量
3. 再做 P2，固化 API / Web 执行
4. 最后接入编排层

## 6. 真实项目使用方式

真实项目只承担验证角色，不承担平台规则定义角色。

建议做法：

1. 选 1 个文档型项目做生成验证
2. 选 1 个流程型项目做执行验证
3. 选 1 个稳定项目做编排验证
4. 验证通过后回收为平台基线

PR-2 仅作为真实项目验证样例，其业务字段、环境变量前缀、接口路径不得进入平台通用规则正文。
