# 平台测试优化可执行任务清单

> 目的：把平台测试优化路线图拆成可落地的任务单，按 P0 / P1 / P2 排序。
> 约束：平台通用版不承载具体项目业务规则；真实项目只作为验证样例。

## 1. P0 基座统一

### P0-1 统一生成契约

- 目标：把测试用例生成字段固定下来
- 任务：
  - 固定场景、步骤、预期、风险、数据依赖、可执行性字段
  - 固定生成结果版本号和差异记录
- 产出：
  - 生成契约说明
  - 生成结果 schema
- 验收：
  - 不同项目按同一字段输出
  - 生成结果可直接进入执行层
- 真实项目复验：
  - 不需要

### P0-2 统一目录和命名

- 目标：让生成物、回写物、证据包、脚本、任务单能稳定归档
- 任务：
  - 统一目录层级
  - 统一文件命名规则
  - 统一 Web / API / 生成 三轨分目录
- 产出：
  - 目录规范文档
  - 命名规范文档
- 验收：
  - 交付包结构可复用
  - 新项目不需重新设计目录
- 真实项目复验：
  - 不需要

### P0-3 统一报告模板

- 目标：让结果回写有统一口径
- 任务：
  - 固定通过 / 待复核 / 待确认 / 缺陷 四类结果
  - 固定证据引用位
  - 固定摘要、详情、结论三段式结构
- 产出：
  - 报告模板
  - 回写模板
- 验收：
  - 生成、API、Web 报告可以对齐
  - 回写字段可被直接复用
- 真实项目复验：
  - 不需要

### P0-4 统一门控

- 目标：确保默认安全、显式 live、风险负向独立控制
- 任务：
  - 默认安全回归
  - 显式 live 开关
  - 风险负向单独门控
- 产出：
  - 门控说明
  - 运行入口约定
- 验收：
  - 无环境变量时默认 skip
  - live 与风险项必须显式开启
- 真实项目复验：
  - 不需要

## 2. P1 用例生成质量

### P1-1 固化生成提示词

- 目标：让 AI 生成的用例稳定成型
- 任务：
  - 步骤与预期结果成对
  - 禁止模糊断言
  - 引用知识库来源
- 产出：
  - 提示词模板
  - 生成约束说明
- 验收：
  - 用例结构稳定
  - 步骤和预期不缺对
- 真实项目复验：
  - 必须做

### P1-2 增加生成后质量门禁

- 目标：减少人工补写和返工
- 任务：
  - 缺 `result` 拒绝
  - 模糊词扫描
  - 重复场景检查
  - 覆盖缺口检查
- 产出：
  - 质量门禁脚本或规则
  - 拒绝原因说明
- 验收：
  - 不合格用例自动拦截
  - 拒绝理由可读可回修
- 真实项目复验：
  - 必须做

### P1-3 固化场景版本

- 目标：避免 prompt 一改就失去对比基线
- 任务：
  - 生成结果按版本号留档
  - 版本变更保留差异说明
- 产出：
  - 版本留档规则
  - 差异对比格式
- 验收：
  - 同一项目多版本可追踪
  - 差异可回溯
- 真实项目复验：
  - 建议做

### P1-4 输出生成质量报告

- 目标：让生成质量可以评估
- 任务：
  - 输出场景数量、覆盖比例、缺失项、可执行率
  - 标记待确认与待复核项
- 产出：
  - 生成质量报告模板
  - 质量统计脚本或流程
- 验收：
  - 能一眼看出生成质量
  - 能定位缺口
- 真实项目复验：
  - 必须做

## 3. P2 API / Web 执行层

### P2-1 固定 API 分层

- 目标：让接口测试按同一框架展开
- 任务：
  - 固定准入 / 查询 / 写入 / 复合 / 负向 / 收口 六层
  - 单接口测规则，复合场景测闭环
- 产出：
  - API 分层清单
  - pytest 目录骨架
- 验收：
  - 新项目可直接套用
  - 不需要重设计测试层级
- 真实项目复验：
  - 必须做

### P2-2 固定 Web 稳定层

- 目标：让 Web 测试能长期复跑
- 任务：
  - 主链路
  - 分层回归
  - 负向隔离
  - 结果回写
- 产出：
  - Web 回归运行手册
  - 稳定脚本模板
- 验收：
  - 页面流程、明细、结果弹窗一致
  - 关键场景可复跑
- 真实项目复验：
  - 必须做

### P2-3 统一证据链

- 目标：让 Web 和 API 的证据能合并成同一份结论
- 任务：
  - Web：截图、self_reflect、页面明细
  - API：返回体、DB / 流水、pytest 报告
  - 编排：统一执行报告
- 产出：
  - 证据模板
  - 回写模板
- 验收：
  - 证据项完整
  - 结论可追溯
- 真实项目复验：
  - 必须做

### P2-4 接入编排入口

- 目标：支持一条指令驱动双轨执行
- 任务：
  - 场景选择
  - 自动分轨
  - 自动聚合回写
  - 门控保持
- 产出：
  - 编排入口文档
  - 编排执行报告格式
- 验收：
  - 能串起选场景、执行、回写
  - 默认零写入
- 真实项目复验：
  - 必须做

## 4. 真实项目复验安排

### 4.1 复验顺序

1. 先做生成质量复验
2. 再做 API 只读复验
3. 再做 API live 小额复验
4. 再做 Web 主链路复验
5. 最后做编排联动复验

### 4.2 复验样例类型

- 文档型项目：验证需求 → 用例生成
- 流程型项目：验证多步骤、状态机、边界生成
- 稳定项目：验证 API / Web 编排联动

### 4.3 复验通过条件

- 生成结果稳定
- 执行结果稳定
- 回写结果稳定
- 可以冻结为平台基线

## 6. 任务优先级建议

| 优先级 | 任务 |
|---|---|
| P0 | 统一生成契约、目录和命名、报告模板、门控 |
| P1 | 提示词、质量门禁、版本留档、生成质量报告 |
| P2 | API 分层、Web 稳定层、证据链、编排入口 |

## 6. 结论

先把平台标准固定，再让生成质量可控，最后把 API / Web 执行做成可复跑资产。
真实项目复验放在 P1 和 P2，用来验证平台能力，不反过来定义平台规则。
