## 一、为什么先分诊，而不是接着盲跑

上一轮的第二批实测（TR-837~841）4 条全 `checks=0`，每条白烧 12–169 秒。原因不是环境，
而是 **`requirement_rule.rule` 写成流程叙述时，编译器提取不出可判断言**。所以"有规则文本"
只是必要条件；**能不能编译出带用例归属的检查**才是充分条件。

分诊就是只问这一个问题，而且问得很便宜：

| 动作 | 耗时 | 说明 |
|---|---|---|
| `POST /web-case-links/minimal-loop`（只编译，不建 run、不执行） | **0.4–1.2s / 规则组** | 返回 `compile_receipt` + 生成脚本 |
| 读脚本里的归属数据 | ~0 | `"case_id": "TC-xxxx"` 出现在 FORM_PLAN.checks / COLUMN_CONTRACT.owners / SORT_CHECKS[].owners |
| 跑一条要用的时间（对照） | 56–170s | 且零断言时同样只得到 NOT_EXECUTED |

**归属判据与运行期断言账本同源**：账本只认带 `case_id`（或 owners 展开）的检查；
脚本里没有这个 case_id，运行时就不可能有用例级结论。所以编译期读到的集合 = 运行期能拿到的集合。

### 为什么"一个规则组一个 run"，不是"一条用例一个 run"

实测：一条 run 只编译**一个主用例**的断言（`compiled_cases.case_count=1`），但归属会覆盖
**规则文本完全相同**的同批用例——TR-833 里 20 条用例只跑 1 个脚本，8 条同规则用例拿到同一结论。
所以正确单位是**规则组**：164 条候选只对应 56 个组，执行 9 个组就把 17 条全判完。

## 四、本轮抓到并修掉的三个真问题

### 4.1 后端会「自己把自己杀掉」——这是基线整批中断的根因（影响最大）

TR-850（支付 3 条）跑完把三条用例全写成 NOT_EXECUTED，作业错误信息是
「执行被中断（服务器重启或进程终止）」。日志里的真实原因不在业务代码：

```
web_test_service.py:1100  zip_path.unlink()
  → sitecustomize._safe_path_unlink        （WorkBuddy 注入的站点补丁）
  → _check_bulk_delete_guard               （同一"回合"内第 50 次删除触发阈值）
  → SystemExit(1)                          （进程直接退出，不是异常！）
```

`SystemExit` 不会被 uvicorn 的异常处理兜住，**整个后端进程退出**，正在跑的 run 全部中断。
这是环境侧注入（`PYTHONPATH` 指向 shim 目录）导致的，不是平台 bug，但会把基线跑批做成"随机丢结果"。

**修法**：后端用干净环境启动——
`env -u PYTHONPATH -u CODEBUDDY_SAFE_DELETE_ENABLED -u CODEBUDDY_SAFE_DELETE_BULK_GUARD .venv/Scripts/python.exe -m app.main`
**验证**：改后连续 9 个 run（TR-856~864）零中断，全部跑到终态。

### 4.2 子菜单选择靠「用例文本关键词」→ 没有实体词的用例会跑到店铺列表

TR-853（商品「已鎖定」那条）结论 FAILED、`matched=0/6`，日志却是
`YL_LIST_READY rows:0` + `page_count=16` + extra 表头 `Store Code/Store Name…`——
**页面是店铺列表，不是商品列表**。同子功能的 TR-847 是 `page_count=10 / matched=6`。

根因：`_yl_masterdata_child_menu` 按用例名/规则文本里的实体词选子菜单；用例名是
「列表顯示-YL-主数据管理（已鎖定…）-欄位完整性校驗」，不含"商品"，于是落回默认分支。

**修法**：用 rev202 就支持的配置覆盖，不动代码——
`web_sub_functions.custom_config.field_locators.child_labels`
（店铺 `["Shop Management"]`、商品 `["Item Manage"]`、支付 `["Payment Method"]`）。
**验证**：TR-856/857（商品 4 条）、TR-858~861（支付 8 条）全部 PASSED。

### 4.3 两条用例 `module` 为空 → base_url 落占位，attach 直接 400

TC-405041 / TC-689853（都是「已鎖定」系列）`custom_fields.module` 为空，
attach 报 `[placeholder_base_url] base_url 仍为占位地址（example.invalid）`。
已补 `module` = `YL-主数据管理-商品` / `YL-主数据管理-支付方式`（附 `module_source=backfill_20261026`）。
注意：补 module 只解决"能进页面"，**进哪个子菜单仍由 4.2 的 child_labels 决定**，两者不能互相替代。

## 五、还没解决的

1. **83 条导入类用例没有落点**：TR-865 实测「導入任務列表」子菜单不存在，可见菜单只有
   Member Center / Loyalty Program / Tag Center / Promotion Management / Coupon 等；
   独立菜单探针（TR-827）也确认 MDM 只有 Order List / Brand / Shop / Item / Payment 五项。
   要么等 MDM 提供入口，要么改走 API 通道（导入接口）。
2. **36 条筛选条件 + 24 条只读态没有执行通道**：这是编译器能力缺口，不是数据问题。
   合计 60 条 = 当前可判规模（20）的 3 倍，值得单独立项评估。
3. **商品列表当前 0 行数据**（`rows:0, empty:true`，表头 10 列正常）：列契约靠表头仍可判，
   但商品侧任何"排序/行级"校验都只能 unverified。店铺列表有 10 行、支付有 10 行。
4. **2 条负路径用例卡在 unverified**：CS 列表搜索「按 Case No. 过滤」提交后窗口内没抓到目标接口请求；
   CS 发邮件「多收件人」前置条件未构造成功。两条都只拿到部分断言，按 rev203 口径降为 SKIPPED。
5. **店铺 15 欄位缺 3 列**（優先級 / 是否在APP顯示 / 所屬組織）：已知缺陷，4 条红固定出现，
   IDP 单号回填后应单列"已知缺陷"档，不与新增失败混计。

## 六、下一步建议（按性价比排序）

1. **把这 20 条可判用例固化成"基线一轮"**（12 个 run，跑完约 25 分钟；排除 TR-867 这种
   13 分钟的慢脚本后约 12 分钟），每次发版跑一轮，只看「PASSED 数 / 已知缺陷数 / 新增失败数」三个数。
2. 再决定是否为「筛选条件」「只读态」补通道：60 条用例的覆盖面 vs 编译器改造量。
3. 导入 83 条单独拉一条线（API 通道），不混在 UI 基线里。
4. 把「规则文本 → 是否可编译」做成用例入库时的体检项（编译期即可判，13 秒跑完全库），
   避免再往基线里塞注定 NOT_EXECUTED 的用例。
