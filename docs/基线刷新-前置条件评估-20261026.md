## 二、三个阻塞（按严重度排序）

### 阻塞 1：列表域没有断言归属 —— 跑出来全是 NOT_EXECUTED

实测证据：

| run | 日志证据 | 用例级结果 |
|---|---|---|
| TR-820（支付） | `COLUMN_DIFF match 7/7`、`SORT_PHASE pass:1`、job `completed` | `test_results.status = **NOT_EXECUTED**` |
| TR-821（商品） | 排序 pass、列 6/8 | 同上 |
| TR-828（商品复核） | `COLUMN_DIFF match 6/6`、`SORT_PHASE pass:1`、`1 passed` | `case_attributed_total = 0` |
| TR-813 ~ TR-828（全部 16 个 YL run） | — | `case_attributed_total/pass/fail` **全为 0** |
| 对照：TR-810（问卷） | 脚本输出 `COMPILED_ASSERTION` | `case_attributed_total = 45 / pass 38 / unverified 7` |

根因：`assertion_ledger` 只认 stdout 里的 `COMPILED_ASSERTION {name,outcome,case_id,rule_id}` 行
（`backend/app/services/assertion_ledger.py:41`）。列表域的列契约与排序判定走的是
`COLUMN_DIFF` / `SORT_TRACE` / `SORT_PHASE` 三行**诊断日志**，不带 `case_id`，
于是既不进 `case_attributed`，也不进 `config_only`，账本里等于不存在。
TR-828 的 `COMPILED_COVERAGE` 也是 `assertions: 0`、`field_labels_missing: ["列表顯示欄位","列表"]`。

> 影响：`1 passed` 只是 playwright 层的 test 粒度，用例级永远是「未执行」。
> 拿这个去刷基线，报告会显示 0 条通过、0 条失败——毫无判读价值。

### 阻塞 2：一次 attach 只跑一条用例

`create_minimal_loop` 用 `_select_test_case` 选**一个主用例**生成 1 个 WebTest / 1 个 spec，
批次里其余用例只进 manifest 做覆盖率统计（`COMPILED_COVERAGE.cases=2`，但脚本里
`Running 1 test using 1 worker`，test 标题只有 `... - TC-135088`）。

所以「855 条」不是「一次跑批 60 分钟」，而是 **855 个 run**：

- 单 run 实测：脚本执行 39–44s + 编译/attach ~10s + 排队；
- 保守估算 855 × 55s ≈ **13 小时**（不含重跑）；
- 且每个 run 只有那 1 条主用例可能被判定，其余同批用例仍是 NOT_EXECUTED。

### 阻塞 3：导航有约 50% 的首次失败率（环境侧，非产品缺陷）

| run | 第 1 次 | 第 2 次 | 第 3 次 |
|---|---|---|---|
| TR-818 | 失败：`YL_MENU_DUMP []` | **通过** | — |
| TR-825 | 失败：菜单未展开 | **通过** | — |
| TR-828 | 失败：菜单未展开 | 失败：同样 | **通过** |

失败时的 `FRAME_DIAG` 很清楚：`frame#1 name="systemIframe"` 里 11 个菜单项**齐全**
（含 Master Data Management），但 `scope` 侧取不到 → iframe 内菜单渲染时序问题。
判据：环境可达（两个入口 curl 均 200），不是 WAF、不是频控。

批量跑批若不带重试，会产生一批**纯环境假失败**混进基线。

## 三、结论与建议顺序

**不要现在开跑基线刷新。** 先补两件事，再跑：

1. **rev203：让列表域的检查进断言账本**
   把 `COLUMN_DIFF` 与 `SORT_PHASE` 的 verdict 同时输出成 `COMPILED_ASSERTION`
   （带 `owners` 里的 `case_id` / `rule_id`，outcome 取 match/unverified/fail）。
   编译器侧已有 `owners` 通道（`web_case_compiler.py:4023`），工作量在模板层。
   验收口径：单条 run 的 `case_attributed_total ≥ 1`，且 TR-820/828 的用例状态从
   NOT_EXECUTED 变成 PASSED/FAILED。
2. **导航重试**：`yl-menu-expand` 失败时整段重试 1–2 次（现在只重取一次 scope，不重进页面），
   把首次失败率压到可忽略。
3. 做完 1+2 后，先跑 **20 条小批**验证：归属数是否 = 用例数、单条耗时、失败里环境侧占比。
   小批达标再放量。

放量口径建议改成「按子功能分批」而不是「按全库」：先跑列表域 3 个子功能（店铺 520 / 商品 81 / 支付 58 = 659 条），
CS 类 8 个（~81 条）看归属是否正常，最后再谈全量。

## 五、rev203 修复与验收（13:37–14:00，已完成）

### 改了什么

**① 列契约 / 排序结论进断言账本**（`web_case_compiler.py` + `web_case_link_service.py`）

- 列契约合成时带 `owners`（一份列清单常被多条用例重复声明 → 合并、按 case_id 去重）；
- `columnDiag` 在 `assert_on_mismatch === true` 时按 owners 逐条输出
  `COMPILED_ASSERTION`：`match→pass` / `mismatch→fail` / `no_header→unverified`；
- `sortDiag` 的 pass / fail / unverified 三分支同样按 owners 输出；
- **诊断型契约不记账**（`assert_on_mismatch !== true` 直接 return）：配置漂移不是用例失败。

**② `fail` 不再被判成 SKIPPED**（`web_case_result_mapper.py`）

旧 `aggregate_status` 只认 `blocked`，`fail` 落 else 分支 → SKIPPED，
导致**用例级永远不可能出现 FAILED**：真实失败被记成"存在断言但没能验证"。
已改为 `fail → FAILED`，并守住 `unverified → SKIPPED` 不升级。

**③ 菜单展开失败自动恢复**（`_NAV_RECOVERY_TEMPLATE`，rev203 新增）

- 三次作用域都失败 → 整页 `reload` 重走一次（复刻"重跑即过"，boc_auth 在 URL query 里不丢登录态）；
- 失败现场改为**双作用域 + DOM 明细**：老实现 dump 时 `scope` 已被改成 `appPage`（console 空壳，
  bodyLen=3），于是 `YL_MENU_DUMP []` 恒为空——看到"菜单为空"其实是被自己的日志骗了。

### 验收结果（真实 UAT）

| run | 子功能 | 日志判定 | 用例级结果 |
|---|---|---|---|
| **TR-829** | 商品 | `COLUMN_DIFF match 6/6`、`SORT_PHASE pass 1` | **2 PASSED**（TC-135088 列契约 / TC-568711 排序） |
| **TR-831** | 支付 | `COLUMN_DIFF match 7/7`、`SORT_PHASE pass 1` | **2 PASSED**（TC-380465 / TC-568711） |

## 六、14:40–15:00 rev204：行数据等待 + 开跑第一批（含规模口径再纠偏）

### 6.1 rev204 修的是「就绪 ≠ 有数据」

TR-830 里 `SORT_TRACE why=no_rows` 曾被读成「店铺列表没数据」。实测证否：

| 观测 | 结果 |
|---|---|
| `GET /yundt-saas-gateway/api/icdp/v1/org/shop/list?pageNum=1&pageSize=10` | HTTP 200，`endRow=9`（10 条） |
| 页面 `.ant-table-tbody` 数据行 | 10 行，全部可见，首行 `15805 / 店铺名称-中文 / …` |
| 连续 25s 采样 | 行数恒为 10，无空态 |

根因：`YL_LIST_READY` 只看 `.ant-table` 可见（thead 一出就通过，实测 1.27s），
排序采样正好落在「thead 已渲染、tbody 未挂数据」的窗口。
改动：①就绪判据加「有数据行 或 有空态」；②`sortColumnSample` 无行时轮询等待 12s。

**TR-832 验收（同 5 条）**：`YL_LIST_READY rows:20`、`SORT_PHASE pass 1`、
TC-700980 由 SKIPPED → **PASSED**（rows=10 单调递减），4 条列契约仍 FAILED（已知缺陷）。

### 6.2 规模口径第三次纠偏：855 → **184**

之前算的「绑定了子功能 879 / 可编译 855」还是高估，因为**大部分用例的 `requirement_rule.rule` 是空的**：

| 口径 | 数量 |
|---|---|
| 全库用例 | 2890 |
| 绑定子功能 | 879 |
| 绑定 + **有规则文本** | **184**（21%） |
| 有规则但未绑子功能 | 337（拿不到通道） |
| 子功能维度 | 店铺 520/120、商品 80/26、支付 59/18、问卷 70/16 |

⇒ 基线的真实可判规模是 **184 条**（≈184 个 run，按单 run ~70–110s 估算 4–5.5 小时），
不是 855 条 13 小时。「有空规则」的 695 条无论跑多少轮都只会是 NOT_EXECUTED，
属**数据待补**，不是执行能解决的问题。批次清单见 `docs/基线批次清单-20261026.csv`。

### 6.3 第一批实测（TR-833，店铺 20 条）

| 结果 | 条数 | 说明 |
|---|---|---|
| PASSED | 8 | `input_validation:店鋪編號 [30字]/[31字]` 两类检查全过 |
