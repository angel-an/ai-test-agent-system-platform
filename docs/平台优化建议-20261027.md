# AI 智能平台优化建议（平台产品自身）— 2026-10-27

> 范围：平台自身功能（API 端点入库 / api-tests 执行链 / 生成脚本质量 / 资产管理），
> 不含为被测业务服务的测试生成框架（那部分见《框架优化建议-20261026》）。
> 每条带代码行号或落库数据证据，按影响分级。

---

## P0-1：api-tests 执行链从未产出结构化结果 —— reporter 配置缺失（实锤）

**根因链**（`backend/app/services/api_test_executor.py`）：

1. `_generate_playwright_config`（L232）生成的 config **没有配 reporter**；
2. `_run_playwright_test`（L304）命令行只传 `--reporter=@playwright/test/allure-playwright`；
3. 但 `_run_playwright_test`（L326）随后读 `work_dir/results.json` —— 那是 **json reporter 的产物**，从来没被配置过；
4. 于是永远走 fallback 分支（L336）：返回 `{"status": passed/failed, error, stdout}`，**没有 suites**；
5. `_process_test_results`（L376）拿 `suites=[]` 循环零次 → `total_tests / passed / failed` 全零，且：
   - **不落任何 per-test 结果**（test_results 表对 API run 是空的）；
   - **`_process_idp_defect` 永不触发** —— 失败→缺陷登记这条链路整个空转；
   - skipped 恒 0。

**落库证据**：`api_test_runs` 全库 **101 个 run 的 total_tests=0**（约占全部 run 的 2/3），
其中多个 `status='completed'` 但 `total=passed=failed=0` —— "完成"却没有任何结果明细。

**修法**（一处命令行改动）：reporter 链同时输出 json + allure：

```
--reporter=[["json",{"outputFile":"results.json"}],["@playwright/test/allure-playwright"]]
```

**验证**：跑一次 run，`total_tests>0`、per-test 结果落库、失败用例能进缺陷登记闸。

## P1-2：生成的 API 脚本丢弃 query 参数、path 参数一律替换成 "1"

`api_case_link_service.py`：

- `_sample_headers`（L871）只取 `in=header` 的参数，**`in=query` 全部丢弃**；
- `_sample_path`（L866）把所有 `{param}` 替换成字面量 `"1"`。

**后果**：带参接口的"契约测试"实际打的是残缺 URL —— 要么 404/500，要么打中
"查询不存在资源" 返回 `200 + data:null`（信封断言照过，**假通过**）。
最小闭环入库的端点越多，这类无效绿色结果越多。

**修法**（一期，不过度）：`options` 增加 `params`，只取 `required=true` 的 query 参数
（样本值优先 `default`，否则 `"test"`）；可选参数一期不传（避免样本值撞业务校验）。
path 参数维持 `"1"` 但**在脚本注释/日志里显式标注**"路径参数为占位样本值"，
让读报告的人一眼知道这类结果的可信边界。

## P1-3：结果解析只看布尔 `ok`，不读 `status` —— skipped/timedOut 语义丢失

`_process_test_results`（L392-396）用 `test.get("ok", False)` 二分通过/失败。
Playwright JSON 里 test 有完整 `status`（`passed / failed / skipped / timed out / interrupted`）：

- `test.skip()` 守卫触发的用例（如缺环境变量、变异接口默认禁跑）会被算成 failed 或 passed，两头都不对；
- `timed out` 与业务断言失败混在同一个 failed 里，无法区分环境慢和真缺陷。

**修法**：按 `test.status` 分派状态映射；与 P0-1 同文件同函数，顺手一起改。

## P2-4：模板/编译器升级不重生成既有脚本 —— 资产会悄悄过期

minimal-loop 对已存在的 api-tests **复用不重新生成**（复用本身是对的，省时省钱），
但代价是脚本停留在生成当日的模板版本：当前 55 个 api_tests 资产里
5 个早于 10-23 的执行器/模板修复，其脚本里还是旧逻辑。

**修法建议**（低侵入）：`api_tests` 记录生成时的 compiler_rev（已有该机制的字段沿用）；
列表/详情页能按 "rev 落后" 过滤，并给一个**手动**"按最新模板重生成"按钮——
不做自动批量重生成（会覆盖用户改过的脚本，风险大于收益）。

## P2-5：生成的 Playwright config 里有无效配置

`_generate_playwright_config`：`slowMo: 3000` 是**浏览器**启动选项，纯 API 测试
不启动浏览器，无害但误导排查；`retries: CI ? 2 : 0` 写死。一期可只删 slowMo 并加注释，
retries 留到有真实重试诉求再配置化。

## 建议的投入顺序

| 顺位 | 事项 | 量级 | 理由 |
|---|---|---|---|
| 1 | P0-1 reporter 修复 | 半天 | 解锁 per-test 结果 + 缺陷登记链路，是"结果可信"的地基 |
| 2 | P1-3 status 分派 | 0.5h 内 | 与 P0-1 同函数顺手改，补齐 skipped 语义 |
| 3 | P1-2 query 参数 | 1-2h | 消灭最大一类假通过 |
| 4 | P2-4/P2-5 | 各半天内 | 资产保鲜与卫生，可等前三个稳定后做 |

## 不建议做

- 自动批量重生成脚本（覆盖风险 > 收益）；
- 给 P1-2 的可选 query 参数造业务真实数据（数据构造属另一层，一期不做）。

## 七、已实施记录（2026-10-27）

P0-1 + P1-2 + P1-3 全部落地，实测中又牵出两处更靠前的断点，一并修好（都属于同一条"结果不可信"链路）。

### 实际根因链（比原判断多两层）

| # | 断点 | 后果 |
|---|---|---|
| 1 | config 未配 reporter，命令行只传 allure | `results.json` 永不生成 |
| 2 | **allure-playwright 这个第三方包根本没装** | Playwright 在解析 reporter 阶段就 `MODULE_NOT_FOUND` 退出，**一个测试都没跑**，run 仍记 `completed` |
| 3 | `--reporter=[["json",{...}]]` 数组形式在 Windows 被 CLI 拆错 | 报 `Cannot find module '[["json"'` |
| 4 | `_save_test_result(_results=...)` 与调用点 `results=` 不匹配 | 每次落库 TypeError → 外层 except 吞掉 → **计数永不更新** |
| 5 | `subprocess.run` 直接在事件循环里跑（阻塞） | 被测接口在本机时，用例请求打进来服务没人应答 → **必然失败**（同一脚本在服务外跑是 passed） |

### 改动

| 位置 | 内容 |
|---|---|
| `_generate_playwright_config` | reporter 写进配置文件（官方支持写法，避开 CLI 数组拆分）：`[['json',{outputFile:'results.json'}]]`，allure 由 `PW_ALLURE_REPORTER=1` 决定是否追加 |
| `_run_playwright_process` | base_url → `API_BASE_URL`、`execution_config.env` 透传；`asyncio.to_thread` 执行，不再冻结事件循环 |
| `_allure_reporter_missing` | 识别三种报错措辞（Cannot find module / is not defined by "exports" / resolveReporters），仅在**因 reporter 缺失失败**时降级重跑一次 |
| `_map_test_status` | 按 Playwright JSON 真实取值分派：`expected/flaky→PASSED`、`skipped→SKIPPED`、其余→FAILED；缺 status 时回退布尔 `ok` |
| `_process_test_results` | 用例名取 `spec.title`（`tests[].title` 恒为 null）；单条落库失败只记日志、不拖垮整段计数 |
| `_save_test_result` | 形参 `_results` → `results`，与调用点对齐 |
| `api_case_link_service` | 生成的脚本消费必填 query 参数（default → 枚举首值 → 类型样本值），可选参数不传；脚本内注明样本值边界 |

### 已知未修（需单独立项）

1. **IDP 缺陷登记在 API 链路抛 greenlet 错误**：`[IDPDefect] 处理缺陷创建时发生错误: greenlet_spawn has not been called; can't call await_only() here`。日志被"不影响测试结果"吞掉 ⇒ 自动建单实际从未成功。属 session 使用不当（后台任务里做同步 DB 调用），修它要动登记服务的会话来源，风险大于本次范围。
2. `_generate_allure_report` 仍是同步 `subprocess.run`（allure CLI 未安装时只报一行 warning），影响面小。
3. 历史 101 个 `total_tests=0` 的 run 不会回溯修正（属既有数据，不回填）。
