# AI 智能平台优化建议（平台产品自身）— 2026-10-27

> 范围：平台自身功能（API 端点入库 / api-tests 执行链 / 生成脚本质量 / 资产管理），
> 不含为被测业务服务的测试生成框架（那部分见《框架优化建议-20261026》）。
> 每条带代码行号或落库数据证据，按影响分级。

## P0-1：api-tests 执行链从未产出结构化结果 —— reporter 配置缺失（实锤）

**根因链**（`backend/app/services/api_test_executor.py`）：

1. `_generate_playwright_config`（L232）生成的 config **没有配 reporter**；
2. `_run_playwright_test`（L304）命令行只传 `--reporter=@playwright/test/allure-playwright`；
3. 但 `_run_playwright_test`（L326）随后读 `work_dir/results.json` —— 那是 **json reporter 的产物**，从来没被配置过；
4. 于是永远走 fallback 分支（L336）：返回 `{"status": passed/failed, error, stdout}`，**没有 suites**；
5. `_process_test_results`（L376）拿 `suites=[]` 循环零次 → `total_tests / passed / failed` 全零，且：
   - **不落任何 per-test 结果**（test_results 表对 API run 是空的）；
   - **`_process_idp_defect` 永不触发** —— 失败→缺陷登记这条链路整个空转；
   - skipped 恒 0。

**落库证据**：`api_test_runs` 全库 **101 个 run 的 total_tests=0**（约占全部 run 的 2/3），
其中多个 `status='completed'` 但 `total=passed=failed=0` —— "完成"却没有任何结果明细。

**修法**（一处命令行改动）：reporter 链同时输出 json + allure：

```
--reporter=[["json",{"outputFile":"results.json"}],["@playwright/test/allure-playwright"]]
```

**验证**：跑一次 run，`total_tests>0`、per-test 结果落库、失败用例能进缺陷登记闸。

## P1-2：生成的 API 脚本丢弃 query 参数、path 参数一律替换成 "1"

`api_case_link_service.py`：

- `_sample_headers`（L871）只取 `in=header` 的参数，**`in=query` 全部丢弃**；
- `_sample_path`（L866）把所有 `{param}` 替换成字面量 `"1"`。

**后果**：带参接口的"契约测试"实际打的是残缺 URL —— 要么 404/500，要么打中
"查询不存在资源" 返回 `200 + data:null`（信封断言照过，**假通过**）。
最小闭环入库的端点越多，这类无效绿色结果越多。

**修法**（一期，不过度）：`options` 增加 `params`，只取 `required=true` 的 query 参数
（样本值优先 `default`，否则 `"test"`）；可选参数一期不传（避免样本值撞业务校验）。
path 参数维持 `"1"` 但**在脚本注释/日志里显式标注**"路径参数为占位样本值"，
让读报告的人一眼知道这类结果的可信边界。

## P1-3：结果解析只看布尔 `ok`，不读 `status` —— skipped/timedOut 语义丢失

`_process_test_results`（L392-396）用 `test.get("ok", False)` 二分通过/失败。
Playwright JSON 里 test 有完整 `status`（`passed / failed / skipped / timed out / interrupted`）：

- `test.skip()` 守卫触发的用例（如缺环境变量、变异接口默认禁跑）会被算成 failed 或 passed，两头都不对；
- `timed out` 与业务断言失败混在同一个 failed 里，无法区分环境慢和真缺陷。

**修法**：按 `test.status` 分派状态映射；与 P0-1 同文件同函数，顺手一起改。

## P2-4：模板/编译器升级不重生成既有脚本 —— 资产会悄悄过期

minimal-loop 对已存在的 api-tests **复用不重新生成**（复用本身是对的，省时省钱），
但代价是脚本停留在生成当日的模板版本：当前 55 个 api_tests 资产里
5 个早于 10-23 的执行器/模板修复，其脚本里还是旧逻辑。

**修法建议**（低侵入）：`api_tests` 记录生成时的 compiler_rev（已有该机制的字段沿用）；
列表/详情页能按 "rev 落后" 过滤，并给一个**手动**"按最新模板重生成"按钮——
不做自动批量重生成（会覆盖用户改过的脚本，风险大于收益）。

## P2-5：生成的 Playwright config 里有无效配置

`_generate_playwright_config`：`slowMo: 3000` 是**浏览器**启动选项，纯 API 测试
不启动浏览器，无害但误导排查；`retries: CI ? 2 : 0` 写死。一期可只删 slowMo 并加注释，
retries 留到有真实重试诉求再配置化。

## 七、已实施记录（2026-10-27）

P0-1 + P1-2 + P1-3 全部落地，实测中又牵出两处更靠前的断点，一并修好（都属于同一条"结果不可信"链路）。

### 实际根因链（比原判断多两层）

| # | 断点 | 后果 |
|---|---|---|
| 1 | config 未配 reporter，命令行只传 allure | `results.json` 永不生成 |
| 2 | **allure-playwright 这个第三方包根本没装** | Playwright 在解析 reporter 阶段就 `MODULE_NOT_FOUND` 退出，**一个测试都没跑**，run 仍记 `completed` |
| 3 | `--reporter=[["json",{...}]]` 数组形式在 Windows 被 CLI 拆错 | 报 `Cannot find module '[["json"'` |

| 5 | `subprocess.run` 直接在事件循环里跑（阻塞） | 被测接口在本机时，用例请求打进来服务没人应答 → **必然失败**（同一脚本在服务外跑是 passed） |

### 改动

| 位置 | 内容 |
|---|---|
| `_generate_playwright_config` | reporter 写进配置文件（官方支持写法，避开 CLI 数组拆分）：`[['json',{outputFile:'results.json'}]]`，allure 由 `PW_ALLURE_REPORTER=1` 决定是否追加 |
| `_run_playwright_process` | base_url → `API_BASE_URL`、`execution_config.env` 透传；`asyncio.to_thread` 执行，不再冻结事件循环 |
| `_allure_reporter_missing` | 识别三种报错措辞（Cannot find module / is not defined by "exports" / resolveReporters），仅在**因 reporter 缺失失败**时降级重跑一次 |
| `_map_test_status` | 按 Playwright JSON 真实取值分派：`expected/flaky→PASSED`、`skipped→SKIPPED`、其余→FAILED；缺 status 时回退布尔 `ok` |
| `_process_test_results` | 用例名取 `spec.title`（`tests[].title` 恒为 null）；单条落库失败只记日志、不拖垮整段计数 |
| `_save_test_result` | 形参 `_results` → `results`，与调用点对齐 |
| `api_case_link_service` | 生成的脚本消费必填 query 参数（default → 枚举首值 → 类型样本值），可选参数不传；脚本内注明样本值边界 |

## 八、IDP 登记链路修复（2026-10-27 晚）

### 根因（实测更正）

原判断是「后台任务里做同步 DB 调用 / 会话来源不对」，**实测不成立**。真实原因是
**访问了未加载的 ORM 关系**：

```python
if api_test.project and hasattr(api_test.project, "identifier"):   # ← 元凶
```

后台执行会话里的 `api_test` 来自 `session.merge(api_test, load=False)`，
`project` 关系处于未加载状态（默认 `lazy="select"`），在 async 上下文里访问直接抛
`MissingGreenlet: greenlet_spawn has not been called`。异常被外层
「不影响测试结果」的 `except` 吞掉，所以外部现象只是**失败的单子一张都没建出来**。

探针（真实会话、真实 `merge` 语义）实测：

| 阶段 | `register_from_api_failure` 调用次数 | 现象 |
|---|---|---|
| 修复前 | **0** | 只有一行无堆栈 error 日志，链路静默空转 |
| 修复后 | **1** | `source_project_key=PR-2`，继续走到项目映射与建单 |

### 改动（`backend/app/services/api_test_executor.py`）

1. 新增 `_resolve_source_project_key()`：关系已加载就直接读 `__dict__` 里的对象；
   未加载则按 `project_id` **只查 `identifier` 一列**，绝不触发 lazy load。
2. 「不影响测试结果」的 `except` 补上 `exc_info=True` —— 这条链路以后任何异常都留堆栈，
   不再出现「看不见原因、只知道没建单」。
3. 降级分支不再把 Playwright 的**用例状态**当 HTTP 状态码（见下"第二层"）。
4. 新增 `backend/tests/test_idp_defect_project_resolution.py`（7 项）。

### 第二层：修好 greenlet 后立刻暴露的语义错误

真实 HTTP 执行（`ATR-20261027-006`）第一次跑到登记服务，报：

```
TypeError: '>=' not supported between instances of 'str' and 'int'
  defect_decision_service.py:497  _has_sut_evidence
```

根因在降级分支：没采到真实响应时，代码用 `last_result["status"]` 当 `status_code`，
但那是 Playwright 的**用例状态字符串**（`"failed"` / `"timedOut"`），
与 HTTP 状态码是两回事。它一路传到决策层做 `>= 500` 比较就炸。

修法两处：

- `api_test_executor`：降级分支 `status_code` 固定为 `None`（"未知"就是未知，不猜）；
- `defect_decision_service.decide()` 入口增加 `_as_status_code()` 归一化：
  非数字（含 `True`）按"未观测到"处理，数字字符串转 int。
  这是防止其它调用点再传脏值的共用兜底，不改变任何合法输入。

### 实测证据

| 验证 | 结果 |
|---|---|
| 探针（真实会话 + 真实登记服务，末尾回滚） | `project_key=PR-2` / `idp_project=1169` / `priority=medium` / `reqid` 提取成功；记录 `create_status=sync_failed`，错误为 IDP `PERMISSION_ACCESS_TOKEN_EXPIRED`（token 过期，非代码问题） |
| **HTTP 端到端** `ATR-20261027-007`（`base_url` 指向不可达端口造失败） | run `completed / total=1 / failed=1`；`idp_defect_records` **165 → 166**，新增 `source_type=api / project_key=PR-2 / idp_project=1169 / priority=low / create_status=pending`；标题 `【自动化测试】【API】…connect ECONNREFUSED`；日志**无 error**，只有"缺少完整请求/响应证据 → 保持 pending"的 warning |
| 门禁 | `test_idp_defect_project_resolution`(7) + `test_api_environment_block_gate` + `test_defect_registration_decision` + `test_platform_api_execution` + `test_run_verdict` 共 **71 passed** |

`create_status=pending` 而非 `created` 是**设计意图**：这条失败没采到 HTTP 层证据，
按 `allow_create=False` 落 pending 等人工确认，不自动建单。
（该条 pending 是"链路刚打通、登记边界还没收紧"的中间态产物，已在第九节规则落地后清理。）

### 修复后需要人确认的两件事（配置层，不是代码）

1. **自动建单现在是真生效的**：实际生效配置为 `idp_auto_create_enabled=True` / `idp_dry_run=False`。
   此前因 greenlet 报错从未真正建过单，修复后 API 失败会按决策结果**直接调 IDP 建单**。
2. **IDP token 已过期**（`PERMISSION_ACCESS_TOKEN_EXPIRED`），当前失败只会落 `sync_failed` 记录。
   更新 `idp_token` 之前，不要指望单子真的出现在 IDP。

## 九、登记边界：只有被测系统的缺陷才登记（2026-10-27）

**口径（用户确认）**：IDP 只登记**被测系统（SUT）的缺陷**；平台（AI 测试框架自身）
与环境类问题**不登记**，直接修代码。

### 实测发现：这条规则原本并不自动成立

把 11 类失败样本喂给 `DefectDecisionService.decide()`，其中**两类平台/环境问题被判 `create`**：

| 失败形态 | 实际性质 | 修复前 | 修复后 |
|---|---|---|---|
| `apiRequestContext.get: connect ECONNREFUSED 127.0.0.1:1` | 请求没到被测系统 | **create** | skip |
| `Cannot find module '@playwright/test'` | 平台执行依赖缺失 | **create** | skip |
| `Package subpath './allure-playwright' is not defined` | 平台 reporter 缺失 | **create** | skip |
| `NoSuchKey ... script_path` | 平台脚本资产不存在 | **create** | skip |
| `net::ERR_CONNECTION_REFUSED`（浏览器侧） | 环境 | skip（已有规则） | skip |
| 定位器 / 交互超时 | 自动化层 | skip（已有规则） | skip |
| 断言失败 / HTTP 5xx | **被测系统** | create | **create（应保留）** |

根因：`net::ERR_` 只覆盖**浏览器**网络层；API 测试走 `apiRequestContext` 时根本不产生这族文案，
连接层只表现为 `connect ECONNREFUSED`，原规则表未命中 ⇒ 判 `create`。

### 改动（`backend/app/services/defect_decision_service.py`）

在 `NON_SUT_FAILURE_RULES`（只在**无 SUT 证据**时生效的既有规则表）补两条，不新增机制：

1. 连接层错误码封闭集合：`ECONNREFUSED|ECONNRESET|ETIMEDOUT|ENOTFOUND|EAI_AGAIN|getaddrinfo|socket hang up`
   → 「环境类失败（请求未到达被测系统）」
   （刻意不用宽泛的 `request ... failed`，那会误伤 SUT 的真实报错）
2. 平台运行时故障：`Cannot find module|MODULE_NOT_FOUND|ERR_MODULE_NOT_FOUND|Package subpath|NoSuchKey`
   → 「平台运行时故障（依赖缺失或脚本资产不存在）」

### 双向端到端实测

| run | 造法 | 结果 |
|---|---|---|
| `ATR-20261027-008` | `base_url` 指向不可达端口（环境类） | `failed=1`，**缺陷记录 0 条**（skip 直接返回，不落库，仅日志留痕） |
| `ATR-20261027-009` | `base_url` 指向 `127.0.0.1:8000/api/v2/nope`（SUT 返回真实 404） | `failed=1`，**记录 1 条**：`pending / PR-2 / idp_project=1169`，标题「断言失败：期望 < 300，实际 4xx」 |

即：**环境/平台问题不进登记，被测系统的真实响应才进登记**，两个方向都实测到了。
门禁：相关 6 个文件 **97 passed**（新增 3 项锁定两条规则 + SUT 反向保护）。

### 遗留（下一步才做，本次不动）

真实 SUT 失败目前只落 `pending`（不自动建单）：Playwright 的 **JSON 报告里没有
`results[].request` / `response` 结构**，`has_complete_evidence` 恒为 False ⇒ `allow_create=False`。
要让满足条件的 SUT 失败真正自动建单，需要从 trace 或 `APIRequestContext` 附件里补证据，
属独立议题。
