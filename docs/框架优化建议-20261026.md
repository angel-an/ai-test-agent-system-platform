# 爱测平台框架优化建议（基于 2026-10-26 基线实测）

- 依据：本轮把 YL/CS 全项目 184 条用例做完了编译期分诊 + 20 条可判用例实跑，
  加上 2026-10-22/23 C 端下单链路、10-23 平台两处缺陷修复的实测记录。
- 口径：**只列能对上 TR 编号或文件行号的**，不写「感觉上应该优化」。
- 结论先行：框架当前最大的瓶颈**不是执行速度，是「用例 → 可执行断言」的转化率（10.9%）**，
  其次是**三类执行通道缺失**和**路由兜底会静默猜错页面**。

---

## 一、P0：影响基线可信度（会导致「假绿」或「全绿假象」）

### P0-1 可判率只有 10.9%，且没有任何生成期门禁

实测：184 条「有规则文本」用例 → 编译期能提取出可判断言的只有 **20 条**。

| 子功能 | 有用例 | 可判 | 比例 |
|---|---|---|---|
| YL 店鋪主數據 | 120 | 5 | 4.2% |
| YL 商品主數據 | 26 | 4 | 15.4% |
| YL 支付方式 | 18 | 8 | 44.4% |
| 導入任務 / CS 三组 | 4 | 3 | 75% |
| 調查問卷 | 16 | 0 | 0% |

根因：规则文本写成**流程叙述**（「点击新增→填写→保存」）时，编译器提取不出可判断言，
于是整组落 `NOT_EXECUTED`。目前只能靠事后分诊（`baseline_rerun.py --triage`）筛，
**用例已经进库了才发现不可判**。

建议：
1. 需求解析阶段就产出 `assertion_plan`（结构化断言清单：字段 + 期望 + kind），
   与用例一起落库，`judgeable` 字段在生成时就标记。
2. 生成期门禁：`judgeable=false` 的用例不静默落库，进「待补断言」池，
   由人补或走模板化重生成——避免基线分母被不可判用例稀释（本轮 164 条里 147 条是噪声）。
3. 规则文本模板化：`列表顯示欄位`/`排序`/`必填` 这类可判形态已能稳定编译（支付方式 44%），
   优先把店鋪那 120 条按这几种形态重写规则文本，比扩编译器见效快。

成本：中（生成期改造）+ 小（规则文本重写，纯数据）。

### P0-2 缺三类执行通道：筛选 / 只读态 / 地图（共 64 条，占不可判的 35%）

| 不可判原因 | 条数 | 现状 |
|---|---|---|
| 需导入任务入口（MDM 实测无该菜单） | 83 | 入口不存在，非通道问题 |
| 列表筛选条件 | 36 | **无列表筛选通道**（当前只有列契约/排序） |
| 字段只读态 | 24 | **无只读校验通道**（kind 白名单里没有只读类） |
| 地图组件交互 | 4 | 无控件通道 |

建议按 ROI 排序做：**筛选（36）> 只读态（24）> 地图（4）**。
筛选通道可以直接复用现有 `COLUMN_CONTRACT` 骨架，扩 `FILTER_CONTRACT`（控件类型 + 值域 + 期望行数变化）；
只读态更便宜——本质是「字段 disabled 属性断言」，属于现有 `visibility` kind 的近邻。

成本：筛选中（2 天量级），只读态小，地图大且只有 4 条（建议先不做）。
导入那 83 条不是通道问题，是 UAT 没有菜单入口，走 API 通道或等环境。

### P0-3 子菜单路由：未命中关键词时**默认猜「店鋪」**，会静默在错页面做断言

`web_case_link_service.py:3435 _yl_masterdata_child_menu()` 末尾：

```python
return "店鋪主數據", ["Shop Management", "店鋪主數據", "店鋪管理", "Shop"]
```

TR-853 实证：用例文本是「已鎖定」系列，不含商品/支付关键词 → 落到默认店鋪 →
`page_count=16, matched=0`，整批无效。当前只能靠 `custom_config.field_locators.child_labels`
人工覆盖（TR-856~861 就是这么救回来的）。

这条最危险的地方不是「跑错」，而是**可能跑出假绿**：店鋪列表恰好也有 Create Time 列，
在错页面上验排序断言可能通过（注释里 rev202 已经记过一次同类问题）。

建议：
1. 兜底改为**显式失败** `ROUTE_UNRESOLVED`（写进 `ISOLATION_BLOCKED` 同族），不再猜店鋪。
2. 根治：菜单路径按 `sub_function_id` **绑定**（数据驱动），文本关键词只作兜底提示。
   现在 `web_sub_functions` 已有 `custom_config`，只差把它变成一等字段（`menu_path`）。

成本：小（半天），收益是消灭一整类假绿。

## 二、P1：影响执行效率与排错

### P1-1 `test_runs` 没有 verdict 字段，只有 run_state，导致「漏数红」

实测：断言失败的 run 终态是 **REJECTED 不是 DONE**。任何「只统计 DONE」的汇总都会
把全部红漏掉——本轮就踩过。`test_runs` 现有 `case_attributed_*` / `config_only_*` 计数，
但没有一个「本次跑到底是过还是不过」的字段。

建议：加 `verdict`（`pass` / `fail` / `unverified` / `mixed`）或提供聚合视图，
并在 API 文档里把 REJECTED 的口径写死。

成本：小。

### P1-2 执行结果解析依赖 allure，缺兜底 → `total_tests=0`

10-23 修完 `POST /api-tests/{id}/run` 永停 pending 后，残余问题是 run 的 `total_tests=0`：
脚本没产出 allure-results 时结果解析层拿不到用例数。

建议：加 exit code / stdout 兜底解析（进程非零退出 ≥ 一条失败），别让「解析不到」表现为「0 条」。

成本：小。

### P1-3 `FORM_PLAN` 是手写 payload 白名单，新增运行期字段必登记（已踩 4 次）

同一个事实写在「表单 schema」和「执行器白名单」两处，加字段时漏一处就静默丢参。
建议从 schema 自动生成白名单，或加一条单测：schema 字段集 ⊆ FORM_PLAN 字段集（不等就红）。

成本：小（单测）+ 中（自动生成）。

### P1-4 后台任务复用请求 session 的坑，可能不止一处

10-23 修的是 `api_test_executor`（`InvalidRequestError: prepared state` + 后台会话不 commit 被 ROLLBACK）。
同一仓库里还发现 `TestRunTestCaseRepository` 里**同名方法定义两次、后者静默覆盖前者**
（`test_run_repo.py:430`），导致 `results` 上报参数不符——Python 不报错，测试也没覆盖到。

建议：
1. 全仓扫「后台任务里用 FastAPI 请求 session / 不显式 commit」的模式，统一走独立 session 工厂。
2. 加一个 lint/单测：同一类内重复定义同名方法就失败（flake8 `F811` 已能覆盖，确认是否在 CI 里开着）。

成本：小。

### P1-5 基线只有快照，没有 diff

`baseline_rerun.py --report` 产出的是「当前状态 CSV」。基线的价值在**本次 vs 上次**：
哪些转红、哪些转绿、哪些新进不可判。现在全靠人比两份 CSV。

建议：run log 已是追加式 jsonl（天然有时序），加 `--diff` 子命令输出三张清单。
这是「基线刷新」从「一次性报告」变成「可持续流程」的关键一步。

成本：小。

### P1-6 后端重启会吞掉在跑的 run，且无续跑语义

实测：TR-850/852 三条用例 `NOT_EXECUTED`，原因是后端进程被环境清理钩子杀掉（见 P2-2）。
`baseline_rerun.py` 侧已做「按规则组跳过已跑」（重跑自动续），但 **run 本身的状态没有恢复**，
库里留着一批假的 NOT_EXECUTED。

建议：run 加 heartbeat（超过 N 秒无心跳 → 标 `ABORTED` 而不是停在 RUNNING/NOT_EXECUTED），
或提供 `--resume` 把非终态 run 重新入队。

成本：中。

## 四、建议的投入顺序（按「防假绿 > 增覆盖 > 提效率」）

| 顺序 | 事项 | 收益 | 量级 |
|---|---|---|---|
| 1 | P0-3 路由兜底改为显式失败 + 按 sub_function 绑菜单 | 消灭一整类假绿 | 半天 |
| 2 | P1-1 `verdict` 字段 | 消灭漏数红 | 半天 |
| 3 | P1-5 基线 `--diff` | 基线从报告变流程 | 半天 |
| 4 | P0-2 筛选通道（36 条） | 可判用例 +36（10.9% → ~30%） | 2 天 |
| 5 | P0-1 生成期 `judgeable` 门禁 | 分母干净，杜绝无效盲跑 | 2–3 天 |
| 6 | P0-2 只读态通道（24 条） | 再 +24 | 1 天 |
| 7 | P1-2~P2 其余 | 排错效率 | 零散 |

**不建议现在做**：地图控件通道（4 条）、导入任务通道（UAT 无菜单入口，做了也跑不起来）。

## 五、一句话总结

框架的「执行引擎」这轮已经被证明可用（12 个 run 零中断跑完 20 条可判用例，
断言归属全部 ≥1），真正的欠账在**上游**：用例能不能变成断言（10.9%）、
断言要验的东西有没有通道（缺 3 类）、以及**路由猜错时会不会假装成功**。

## 六、已实施记录

### rev205（2026-10-26）：子菜单路由未命中不再默认猜测 ✅

对应 P0-3。改动三处：

| 位置 | 改动 |
|---|---|
| `web_case_link_service.py::_yl_masterdata_child_menu` | 返回值 `(label, candidates)` → `(label, candidates, resolved)`；末尾不再无条件返回店鋪分支，未命中任何子菜单标识时返回 `("", [], False)` |
| `_generate_yl_masterdata_script` | 注入 `const MENU_ROUTE_RESOLVED`，未解析时 `test.skip(!MENU_ROUTE_RESOLVED, 'MENU_ROUTE_UNRESOLVED: ...')` —— 复用既有跳过模式，不新增执行路径 |
| `custom_config.field_locators.child_labels` | 显式配置即视为已解析（配置是"菜单名"这个被测系统事实的来源） |

**实测影响面（关键，避免夸大）**：

- 绑定子功能的 184 条用例 → YL 三子功能 **164 条全部正常解析**，可判组/可判用例仍是 **12 / 20**，与改动前完全一致；
- 被判 unresolved 的只有 2 条可判用例（TC-313663 / TC-837310），它们走的是 CS 模板，**根本不经过这个函数**，无实际影响；
- 结论：现有数据上**零触发**，这是一次防御性修复——防的是"以后新增一条不含菜单关键词的用例，静默跑到错页面还报通过"。

**验证方式**：单元测试 62 项通过（其中 rev202 文件新增 5 项覆盖未解析/已解析/配置覆盖三条路径）；真实链路 attach 一条可判用例，生成脚本确认含 `const MENU_ROUTE_RESOLVED = true;` 与拦截语句。

**顺带修掉的两个工具问题**（`baseline_rerun.py`）：

1. 分诊产物按子功能 id 命名后与历史语义命名并存 → 汇总会重复统计。加 `latest_triage_files()` 按 `sub` 取最新一份；
2. 执行流水同步改名，dry-run 复核 12 个可判组 `pending=0`，重跑不会重复消耗时间。

**未做（有意）**：`projects/PR-9/...` 这类项目号硬编码仍在代码里（`_generate_yl_masterdata_script` 的 OCR 回调默认地址）。参数化会改变未设环境变量时的默认行为，属于"可跑通"与"干净"之间的取舍，留待单独评估。
