# 编译产物版本规范（COMPILER_REV）

> 适用对象：修改 `backend/app/services/web_case_compiler.py`（执行器模板、编译逻辑）、
> 修改执行器预算/超时参数、以及在平台上执行任何 Web 自动化脚本的人。
>
> 立规背景：2026-10-19 用旧产物跑 TR-703，**跑满 1745 秒被硬杀、stdout 没有一个字**，
> 与"新产物 1710 秒自行收尾并报超时"从结果上完全无法区分，白烧 29 分钟。
> 当时 657 个脚本全是旧产物，靠人记"哪个是哪版生成的"不可行。

---

## 一、四条硬规则

### 规则 1：改模板/编译逻辑 → 必须 bump `COMPILER_REV`

**什么算"改模板/编译逻辑"**（会改变产物行为）：

- `_FORM_EXECUTOR_TS` 执行器模板（含选择器、等待、轮询、断言执行方式）；
- `compile_cases` / `probe_value_for` / `build_form_plan` / `build_form_plan_for_template` / `render_form_executor` 的函数实现；
- `FORM_CHECK_KINDS` / `LOCATOR_DEPENDENT_KINDS` / `SOFT_CHECK_KINDS` 的取值。

**什么不算**（不会改变产物行为，不需要 bump）：

- 注释、docstring、日志文案、变量重命名；
- 与本文件无关的其他服务。

> 这个边界由 `compiler_source_digest()` 精确实现：它只 hash 上面列出的东西。
> 改日志文案不会让检查变红，所以这条规则不会因为"太烦"而被绕过。

**怎么 bump**：

```bash
# 1. 改 web_case_compiler.COMPILER_REV，例如 rev118 → rev119
# 2. 重新生成受影响用例的脚本（旧产物会被执行期判为 stale，见规则 3）
# 3. 登记新的 digest
python backend/scripts/check_compiler_rev.py --update
# 4. 补一句改动摘要（--update 会写空 summary，请手工补）
```

**强制手段（两道，不依赖任何人记得）**：

| 层级 | 机制 | 结果 |
|---|---|---|
| 提交前 | `.pre-commit-config.yaml` → `check-compiler-rev` | 钩子非零退出，提交被挡 |
| 测试 | `backend/tests/test_compiler_rev_guard.py` | `pytest` 必红 |
| 执行期 | 产物头 `COMPILER_DIGEST` 与当前源码 digest 比对 | 即使 rev 字符串被人改成一样，digest 不同仍判旧产物 |

实测（2026-10-19）：在执行器模板里插入一行注释、不改 rev → CLI `exit=1`，
提示「执行器模板或编译逻辑已变更，当前 digest=280fc823d367，但 rev118 登记的是 8458a07e1c94」；
同一次变异下 `pytest -k current_tree_passes` 也 `exit=1`。

### 规则 2：调参只走环境变量，不改代码默认值

| 参数 | 环境变量 | 默认值 | 作用 |
|---|---|---|---|
| 提交单项看门狗 | `WEB_SUBMIT_ITEM_MS` | 90000（90s） | 单项卡住多久判"未验证" |
| 脚本总预算 | `WEB_TEST_BUDGET_MS` | 由执行器按三层超时算出（1710s） | Playwright `test.setTimeout` |
| 产物严格模式 | `WEB_TEST_STRICT_ARTIFACT` | `auto` | 见规则 3 |

**为什么禁止改代码**：默认值是所有项目共享的基线。为了绕过一次误判就把 90s 改成 600s，
等于把"单项挂死保护"整个废掉——下次真挂死又要烧满 28 分钟。**误判说明阈值对当前场景不合适，
用环境变量针对性地放开**，并在事后判断是否该改默认值（需要 bump 版本、走规则 1）。

**强制手段**：`test_watchdog_budget_is_env_overridable_with_bounded_default` 断言
①模板里 `SUBMIT_ITEM_MS` 必须从 `process.env.WEB_SUBMIT_ITEM_MS` 读取；
②默认值不得大于 180000ms。直接改成 `const SUBMIT_ITEM_MS = 600000;` 会让测试红。

> `WEB_TEST_BUDGET_MS` 由执行器按三层超时不变式计算下发（引擎 > runner > 脚本），
> 不参与本节的"调参"——它是被算出来的，不是被填的。

### 规则 3：产物落后必须重新生成，不接受"明知旧产物还跑"

`WEB_TEST_STRICT_ARTIFACT` 三态，**默认 `auto`**：

| 模式 | `legacy_no_fingerprint`（从没打过指纹） | `rev_mismatch` / `digest_mismatch`（打过指纹但落后） |
|---|---|---|
| `auto`（默认） | 放行，stdout 打 `ARTIFACT_STALE` 告警 | **拒绝执行** |
| `on` | 拒绝 | 拒绝 |
| `off` | 放行 | 放行（仅用于临时排障） |

**为什么不对称**：存量还有几百个 10-17 前的历史产物，默认全拒会让所有人立刻停摆，
结果一定是"把开关关掉"——规则就死了。但**已经打过指纹的资产，跑落后版本一定是错的**
（要么改了编译器没重新生成，要么有人手工回退了脚本），这一档没有放行理由。

拒绝时 `error_message` 以 `[artifact_stale]` 开头，并带 `mode=` 与 `reason=`；
job stdout 首行是 `ARTIFACT_STALE {...}` JSON，可直接筛。

### 规则 4：产物是唯一事实来源

执行期读**磁盘上的脚本本体**判断版本，不读 `web_tests.generation_params`。
两者可能分叉（手工替换、回填历史产物、重新生成失败但记录已更新）。
`generation_params.compiler_rev` / `compiler_digest` 只用于按版本筛资产，不作为执行依据。

## 二、日常操作对照表

| 场景 | 要做什么 |
|---|---|
| 改了执行器模板 | bump rev → 重新生成受影响用例 → `check_compiler_rev.py --update` |
| 只改了注释/日志 | 什么都不用做（digest 不变） |
| 某条用例单项总是误判超时 | `WEB_SUBMIT_ITEM_MS=180000` 启动后端；不要改代码 |
| 想确认某脚本是哪版产出的 | `head -5 <spec>` 看 `COMPILER_REV` / `COMPILER_DIGEST` |
| 想找出所有旧产物 | 扫 `backend/workspace/web_cli/**/test-script.spec.ts`，无 `COMPILER_REV:` 行即历史产物 |
| 临时要跑旧产物排障 | `WEB_TEST_STRICT_ARTIFACT=off`，仅限本地/一次性，**不得写进启动脚本** |
| 清理阶段想全量拒绝旧产物 | `WEB_TEST_STRICT_ARTIFACT=on` |

## 四、已知边界

- **digest 不覆盖各业务模板之外的字符串**（如 `web_case_link_service` 里的头部拼装）。
  改头部拼装不会变 digest；但头部本身就是指纹载体，改动它属于"改指纹协议"，需人工判断是否 bump。
- **`--update` 不是后门**：同 rev 拒绝写入，rev 必须严格大于末条记录。
- **历史产物没有 digest 行**（rev117 及更早）：digest 判据自动跳过，只按 rev 判。
- 版本号命名必须是 `rev<数字>`，否则递增校验判为非法（`-1`）。
